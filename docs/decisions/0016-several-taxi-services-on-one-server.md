# 0016. Несколько служб такси на одном сервере

- Статус: принято владельцем продукта, 1 ноября 2026.
- Меняет: REQ-TEN-01 (отдельный экземпляр на службу) и вопрос о глобальных настройках из #201. Остальное в REQ-TEN-02…08 и AC-02 остаётся в силе и теперь действует внутри одного экземпляра.

## Решение владельца

1. **На одном сервере (экземпляре) работает несколько служб такси.** У каждой службы несколько городов.
2. **Пассажиры и водители у каждой службы свои.**
   - Один телефон в двух службах — это два разных аккаунта.
   - Службы не видят людей друг друга.
   - Так делаются разные такси с разной маркетинговой кампанией.
3. **У каждой службы своё приложение пассажира и водителя** со своим брендом. Приложение знает свою службу заранее.
4. **Над службами стоит владелец платформы.** Он создаёт службы и их первых суперадминов. Суперадмин службы управляет только своей службой.
5. **Деньги у каждой службы свои:**
   - платёжные мерчанты;
   - тарифы и акции;
   - бонусы и долги;
   - журнал денег и отчёты.

   Службы не видят деньги друг друга.
6. **Сотрудники делятся по службам**, а внутри службы — по городам, как сейчас.
   - Настройки, которые раньше были глобальными, становятся настройками службы: бренд, языки, флаги, юридические тексты, причины отмены, правила переводов, интеграции и ключи, сроки хранения данных службы.
   - Их меняет суперадмин службы или сотрудник с правом во всех городах этой службы.

## Модель

- **Новая сущность — служба (`service`):** `id` (это `service_id` из REQ-TEN-02), код, имя, состояние. `instance_id` остаётся одним на сервер.
- **У каждой записи, которая принадлежит службе, есть `service_id`.** Остальное наследует службу по ссылке.
  - `service_id` есть у города, пассажира (`client`), водителя (`driver`) и сотрудника (`staff_user`). У владельца платформы его нет.
  - Заказы, поездки, зоны, адреса, обращения, звонки и прочее наследуют службу через город или через своего человека. Где запросу нужна служба без соединения таблиц, `service_id` хранится копией.
  - Телефон уникален внутри службы: `unique (service_id, phone)`, а не глобально.
- **Город определяется точкой подачи внутри службы пассажира** (REQ-TEN-03/04). Две службы могут работать в одном и том же городе на карте; их полигоны не конфликтуют.
- **Вход и токены:**
  - Приложение передаёт свою службу при входе (код службы из сборки приложения, REQ-TEN-08).
  - Токен несёт `service_id`.
  - Каждый запрос работает только в службе токена. Объект другой службы — 404, как объект другого человека.
- **Права:**
  - `StaffAccess` сначала проверяет службу, затем город.
  - Суперадмин службы проходит проверки городов только своей службы.
  - Владелец платформы (`PLATFORM_OWNER`) управляет службами. Данные пассажиров, водителей и денег служб он без экстренного доступа службы не видит.
- **Настройки:** `ServiceSettings`, флаги, юридические тексты, причины отмены, интеграции, мерчанты, правила переводов и лимиты долга хранятся по службам. Сроки хранения, технические тоже (ADR 0015), задаёт суперадмин каждой службы, для данных своей службы (решение владельца 02.11.2026, см. ниже).
- **События outbox** несут `service_id`; потребители (push, SMS, отчёты) берут ключи и бренд своей службы.
- **Перенос данных:** всё, что есть сейчас, становится первой службой. Её код задаётся при миграции, по умолчанию `default`.

## Порядок работ

Задачи в GitHub, по частям; каждая заканчивается тестами изоляции между двумя службами.

1. **Основа:**
   - служба и `service_id` у города, пассажира, водителя и сотрудника, с переносом существующих данных в первую службу;
   - вход по службе, токен со службой;
   - проверка службы в `StaffAccess`;
   - владелец платформы;
   - уникальность телефона по службе;
   - город по точке внутри службы.
2. **Настройки службы:** бренд, языки, флаги, юридические тексты, причины отмены, интеграции и ключи, мерчанты, правила переводов, лимиты долга, сроки хранения данных службы.
3. **Деньги и отчёты по службе:** журнал, отчёты, сверка, выгрузки.
4. **Приложения:** стартовые данные (bootstrap) по службе, push и SMS от имени службы.
5. **Изоляция:** `AccessIsolationTests` и `StaffIsolationTests` с чужой службой. Каждая операция проверяется и с другим городом, и с другой службой.

## Решение владельца 02.11.2026: Asterisk и сроки хранения

Вопрос был такой: подключение к станции Asterisk и технические сроки хранения одни на сервер. Кто ими управляет:
суперадмин первой службы или владелец платформы?

Ответ владельца: **суперадмин каждой службы задаёт подключение к Asterisk и сроки хранения.**

- **Asterisk:**
  - адрес ARI, пользователь и пароль хранятся по службе, как остальные интеграции;
  - сервер держит поток событий ARI для каждой службы, у которой подключение задано;
  - звонок, канал и запись относятся к службе того подключения, через которое они пришли;
  - голосовой код уходит через станцию службы того, кто входит.
- **Сроки хранения:**
  - вся таблица сроков ADR 0015 хранится по службе: сессии, коды, доставки кодов, события, квитанции, загрузки,
    файлы в карантине, записи звонков;
  - строка, у которой есть служба, удаляется по сроку своей службы;
  - строки без службы (служебные записи сервера: доставленные события outbox, отметки обработанных событий,
    квитанции повторов команд) хранятся **ровно 30 дней**, без настройки (ответ владельца 02.11.2026: «можно просто
    хранить 30 дней»). В таблице сроков службы этих видов нет.
