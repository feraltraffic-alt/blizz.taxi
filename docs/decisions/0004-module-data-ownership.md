# 0004. Модули владеют своими таблицами

- Статус: принято (D)
- Дата: 26 октября 2026
- Основание: REQ-ENG-03, REQ-ENG-04, раздел 21.2

## Контекст

Модули серверного монолита (`identity`, `driver`, `geo`, `pricing`, `operations`, …) живут в одной базе. Spring Modulith проверяет зависимости между Java-пакетами, но не видит SQL: модуль может прочитать или изменить чужую таблицу в обход её правил. Проверка прав сотрудников была написана заново в пяти модулях, каждый читал `staff_user` сам.

## Решение

1. **Пишет только владелец.** Строки таблицы создаёт, меняет и удаляет только модуль, чья миграция создала таблицу. Остальные модули идут через его API в базовом пакете.
2. **Права сотрудников проверяет только `identity`:** `StaffAccess.require(actor, permission, cityIds…)` — `ACTIVE`, право из списка, города в `city_scope`. Вызов до `IdempotentCommands.execute`. Ни один другой модуль не читает `staff_user`, кроме снимка роли в журнале аудита (таблица ниже).
3. **Чтение чужой таблицы в SQL** допускается только как join или подзапрос только на чтение, когда вызов API разорвал бы атомарность или сделал бы горячий путь неприемлемо медленным, и только для перечисленных здесь случаев. Новый случай добавляется в этот список в том же PR.
4. Внешние ключи между таблицами разных модулей не добавляются для новых связей (пример — `ride_order.quote_id`): целостность обеспечивает команда владельца в той же транзакции.

## Разрешённые чтения чужих таблиц

| Читает | Таблица (владелец) | Где и зачем |
|---|---|---|
| `operations` | `driver`, `vehicle` (`driver`) | Подбор кандидатов и проверка класса авто при принятии заказа (`OrderCore.candidates`, `JdbcDispatch`): один запрос с блокировкой и PostGIS-фильтром |
| `operations` | `device_session` (`identity`) | Принадлежность устройства водителю при открытии смены (`JdbcWorkSessions`) |
| `audit` | `staff_user` (`identity`) | Снимок роли сотрудника в момент действия в записи аудита (`AuditLog.record`); `identity` сам пишет аудит, поэтому вызов API образовал бы цикл |
| `identity` | `city` (`geo`) | Проверка, что города, отмеченные сотруднику, существуют (`JdbcStaffDirectory`); `geo` сам зависит от `identity`, поэтому вызов API образовал бы цикл |
| `pricing` | `city` (`geo`) | Валюта и статус города при расчёте цены и выборе тарифа (`JdbcQuoteService`, `JdbcTariffService`, `JdbcVehicleClasses`) |

## Последствия

- Ревью проверяет пункты 1–3; нарушение без строки в таблице выше — повод вернуть PR.
- Если чтение начинает требовать знаний о чужих правилах (статусы, видимость), его заменяют API владельца.
