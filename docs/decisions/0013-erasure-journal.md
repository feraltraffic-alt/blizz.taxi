# 0013. Журнал удалений вне базы

- Статус: принято (D), 27 октября 2026
- Основание: REQ-PRV-04, REQ-PRV-05, T-39, AC-24

## Контекст

Анонимизация клиента (#56) меняет строки в базе. Если базу восстановят из резервной копии, сделанной раньше удаления, клиент вернётся с телефоном и именем. REQ-PRV-05 требует после восстановления повторно применить журнал удалений.

## Решение

1. **Журнал вне базы.** Каждое `ClientAnonymized` записывается в каталог `blizz.privacy.erasure-journal-dir` (`ERASURE_JOURNAL_DIR`): один файл на субъект, только тип, id и время, без персональных данных. Запись делает потребитель outbox после коммита: откаченная анонимизация в журнал не попадает, неудачная запись повторяется.
2. **Повтор при старте.** При каждом запуске сервер сверяет журнал с базой: клиент из журнала, который в базе не `ANONYMIZED`, анонимизируется снова (данные, сессии, событие `ClientAnonymized` для остальных модулей — их обработчики идемпотентны), с записью в аудит от имени системы.
3. **Эксплуатация.** Каталог журнала лежит на отдельном надёжном хранилище и **не** восстанавливается вместе с базой; у него своя политика резервирования (только дописывание). Значение по умолчанию — временный каталог, только для разработки.

## Последствия

- Восстановление базы не возвращает удалённых клиентов (T-39), «удалено в primary» по-прежнему не означает немедленного удаления из всех копий (REQ-PRV-05).
- Повтор анонимизации после восстановления проходит тот же путь, что и первая (#144): данные, известные другим модулям только по телефону (журнал звонков, доставки кодов, контакт чужого заказа), стираются в той же транзакции через `ClientErasing`, пока телефон ещё в строке клиента; телефон не попадает ни в событие, ни в журнал. Обработчики `ClientAnonymized` идемпотентны.
- Водители и сотрудники войдут в журнал, когда для них появится удаление.
