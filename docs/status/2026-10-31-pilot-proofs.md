## Часть 1. Тест обновления базы (AC-20)

Workflow `.github/workflows/upgrade.yml`, влит в #157.

4. Снимок снимается ещё раз и сравнивается с первым, после чего проходит скан инвариантов.

## Часть 2. Аварийные тесты (REQ-QA-01)

Workflow `.github/workflows/faults.yml`, скрипт `scripts/faults/run.sh`.

Сервер останавливается так же, как при `kill -9`, в именованной точке посреди работы (`blizz.faults.crash-at`,
класс `CrashPoints`). JVM завершается сразу, без shutdown hooks: открытые транзакции откатываются, аренды остаются
занятыми. Затем сервер запускается заново, и скрипт проверяет итог. Production-профиль отказывается стартовать с этой
настройкой.

Поддельный банк песочницы теперь пишет журнал (`blizz.payments.fake-gateway-journal`). Он помнит списания после
падения сервера, как настоящий банк, и по журналу видно, сколько запросов он получил.

| Случай | Точка аварии | Что проверяется |
|---|---|---|
| payment | `payment.after-send:TIP`: банк списал чаевые, сервер умер до сохранения ответа | после рестарта воркер только спрашивает банк (CHECK_STATUS). Банк получил **одно** списание, чаевые PAID, водитель получил их один раз |
| outbox | `outbox.after-handler:TripCompleted/notification.order-live-feed`: один потребитель обработал событие, остальные и отметка DONE нет | событие дошло до **всех** потребителей (тот же набор, что у поездки без аварии). Живое сообщение ушло **один** раз, после рестарта не повторилось (слушатель `listen.py` держит своё соединение с PostgreSQL) |
| dispatch | `dispatch.after-accept`: принятие заказа водителем зафиксировано, ответ не ушёл | повтор приложения с тем же `command_id` получает **200** и то же назначение; у заказа **одно** назначение |
| database | все соединения сервера с базой обрываются (`pg_terminate_backend`) под нагрузкой: 4 клиента запрашивают коды входа | ни одного **500**: запрос, потерявший соединение, получает **503 `TEMPORARILY_UNAVAILABLE`** с `retryable` и `Retry-After: 2`; после обрыва проходит целая поездка, и её событие доставлено |

После всех случаев скан инвариантов (I1–I5) чистый.

### Отрицательные контроли

Каждый контроль собирает сервер с одной сломанной защитой (`scripts/faults/breaks/<имя>.patch`). Задание контроля
зелёное, только если выполнены три условия:

- его случай упал;
- упал **по ожидаемой причине** (по тексту в журнале прогона);
- все случаи до него прошли.

Так контроль не может пройти из-за посторонней ошибки. Это действительно произошло в первом прогоне: случай outbox
не запускался, а контроль был «зелёным».

| Контроль | Что сломано | Ожидаемый провал |
|---|---|---|
| payment | воркер считает операцию в SENDING новой и отправляет её снова | «The tip was charged 2 times» |
| outbox | ключ `consumer_inbox` больше ничего не решает (`fresh >= 0`) | «The live message went out 2 times» |
| dispatch | ключ команды принятия случайный, а не `command_id` | «The retry was not answered with the first result» (409) |
| database | обрыв соединения снова отвечает 500 | «A lost database connection was answered with 500» |

### Что нашли аварийные тесты

Обрыв соединения с базой давал **500 `INTERNAL_ERROR`** тем запросам, которые в этот момент были внутри транзакции.
Транзакция при этом откатилась, и повтор с тем же `command_id` безопасен, но клиент видел внутреннюю ошибку без
подсказки о повторе. Встречалось два пути:

- `DataAccessResourceFailureException` (PgJDBC, SQL state 08xxx / 57P01);
- откат на закрытом соединении Hikari: `JpaSystemException` → `TransactionException: Unable to rollback` →
  `SQLException("Connection is closed")` без SQL state. Это 9 ответов из ~800 за 8 секунд нагрузки.

Оба пути теперь отвечают 503 `TEMPORARILY_UNAVAILABLE`, `Retry-After` 2 с (`blizz.api.database-retry-after`).
Любая другая ошибка базы остаётся 500, это закреплено тестом `ApiExceptionHandlerTests`.

### Чего эти тесты не доказывают

- **Обрыв соединения с провайдером** (таймаут, потерянный ответ) здесь не повторяется. Его покрывают тесты платежей
  со сценарием `TIMEOUT` / `LOST_ANSWER` поддельного банка.
- **Push- и SMS-воркеры** после аварии между отправкой и отметкой SENT отправят сообщение ещё раз. Об этом сказано в
  их коде: доставка «хотя бы один раз».
- **Точка аварии в диспетчере** стоит только на принятии заказа. Захват попытки поиска воркером (аренда 30 с)
  проверяется уникальными индексами и тестами конкурентности, но не аварией.
