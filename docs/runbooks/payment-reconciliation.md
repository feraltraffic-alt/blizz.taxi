# Ежедневная сверка карт с провайдером

REQ-LED-07. Сверка сравнивает банковскую выписку с локальными платежами и сохраняет доказательства. Она не списывает, не возвращает деньги и не применяет результаты UNKNOWN: это остаётся за PaymentWorker/CHECK_STATUS.

`PaymentReconciliationMissing` означает, что хотя бы один мерчант не имел успешной полной сверки 26 часов. Возраст считается отдельно для каждого мерчанта, затем берётся максимум; успех другого мерчанта не скрывает проблему. Предварительный sandbox-запуск неполного дня не обновляет этот возраст.

`PaymentReconciliationFailed` означает сохранённый FAILED. Недоступный провайдер, ошибка формата и неизвестный статус не превращаются в пустую успешную выписку. Смотрите только фиксированный `failure_code`; не копируйте сырой ответ, секреты и данные карты в логи или обращение.

```sql
select id, merchant_id, day, state, attempts, failure_code, local_count, provider_count,
       item_count, open_count, finished_at, lease_until
from payment_reconciliation order by updated_at desc limit 100;
```

В админском API список и детали доступны с `payments.retry` и доступом ко всем городам мерчанта. Для мерчанта без городов нужен доступ ко всем городам. Каждый OPEN элемент требует решения с причиной: EXPLAINED, CORRECTED_BY_HAND либо ESCALATED. Решение фиксируется один раз, аудируется и не изменяет деньги. CORRECTED_BY_HAND лишь подтверждает отдельно выполненную корректировку; само решение ничего не проводит.

Один запуск с расхождениями создаёт один PAYMENT/HIGH кейс с `source_key=reconciliation:<run_id>`. Работа с кейсом не заменяет решения по каждому элементу. Счётчики `blizz.payments.reconciliation.items{kind=…}` показывают OPEN элементы шести фиксированных видов, без идентификаторов и персональных данных в метках.

Повтор завершённого дня возвращает тот же неизменяемый снимок. Уникальный `(merchant_id, day, partial)` и ключ элемента `(run_id, reference_fingerprint, kind)` исключают дубли. FAILED и истёкшая RUNNING-аренда допускают новую попытку с тем же id; токен аренды не позволяет позднему ответу предыдущей попытки перезаписать результат. Предварительный sandbox-снимок и полная ежедневная сверка имеют разные идентичности: preview не блокирует будущую полную сверку того же дня. Автоматические повторы и алерт FAILED учитывают полные запуски; preview повторяется вручную. Запрос к банку выполняется вне транзакции БД. Комиссия сохраняется как `fee_minor` в банковских доказательствах, включая чистые строки; она не сравнивается и не проводится до решения владельца о бухгалтерской политике.

Сырой банковский reference может содержать телефон: хранится только отпечаток, привязанный к мерчанту, и UUID известной локальной операции. Банковские поля клиента, cardPan и токены в снимки и события не входят. Причина сотрудника очищается от вставленных номеров и масок карт; не вводите персональные данные в свободный текст.

Официальные источники: [TRANSACTION_LIST](https://wiki.wayforpay.com/en/view/1736786), [SETTLE](https://wiki.wayforpay.com/en/view/852113), [REFUND](https://wiki.wayforpay.com/en/view/852115). Unix timestamps трактуются в UTC; подпись списка — HMAC_MD5 от account;dateBegin;dateEnd. SETTLE/REFUND используют исходный orderReference авторизации. Сопоставляется текущее состояние цепочки под исходным orderReference: AUTH → SETTLE → полный void/refund; CHARGE/TIP независимы. Пополнения и нулевые верификации распознаются по собственным таблицам payments. Частичный локальный refund, неоднозначная цепочка или противоречивые дубли выписки дают FAILED.

Провайдер не обещает, фильтрует ли TRANSACTION_LIST по созданию или процессингу. Основной запрос — предыдущий день UTC с ±2 часами. Если известная цепочка отсутствует, дополнительно запрашивается день создания исходной авторизации с тем же перекрытием; из такой выписки берутся только запрошенные ссылки. Это совместимость с обеими трактовками даты, а не заявленная гарантия провайдера. Максимум 31 дополнительный день на попытку (`blizz.payments.reconciliation.maximum-supplementary-windows`); не старше 30 суток относительно начала наблюдения; отсутствующая ссылка за пределом этого срока даёт `RECONCILIATION_ANCHOR_OUTSIDE_LOOKBACK` без исторического запроса. Превышение числа окон видно как FAILED и требует разбора/изменения лимита, а не объявляется чистой сверкой. Неизвестная нам банковская транзакция в обработке также оставляет FAILED до окончательного результата, чтобы её позднее списание не потерялось после завершения снимка.

Планировщик запускается в 02:15 UTC, после окончания перекрытия; при старте и затем раз в 15 минут проверяет последний полностью доступный день и до 100 FAILED/истёкших RUNNING попыток. Завершённый запуск не делает повторных сетевых запросов. Тестовые таймеры выключены через `blizz.payments.reconciliation.enabled=false`.

Выписка сообщает текущее состояние выбранных банковских ссылок, а не гарантированный исторический снимок на полночь. `observed_until` фиксирует начало наблюдения; локальные цепочки перечитываются после сетевых запросов. Если их факты изменились между начальным и конечным чтением, запуск получает `RECONCILIATION_LOCAL_CHANGED`/FAILED без элементов и кейса; следующая попытка сравнивает стабильное состояние. Чтения не блокируют финансовые команды. UNKNOWN_STILL учитывает тип команды: стоящий hold ещё не окончательный ответ на неизвестный SETTLE/REFUND. Команда и её результат не применяются сверкой.
