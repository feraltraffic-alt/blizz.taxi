# Техническое задание: платформа заказа такси
Версия 0.2 · 26 октября 2026 года

Основание: согласованный документ Taxi_Platform_Architecture_v0.1.md.
Статус: детализированный проект ТЗ для обсуждения и последующей реализации. Ранее согласованный базис сохраняется. Новые правила и числовые параметры в настоящем документе являются предложениями до утверждения заказчиком. Раздел 36 содержит последующее прямое указание владельца продукта о четырёх таблицах пользователей; это утверждённое уточнение B. Документ не является отчётом о готовности существующего кода.

## 1. Назначение, обозначения и порядок решений

Платформа предоставляет заказ поездок по модели Bolt/Uber и позволяет поставлять самостоятельным службам такси единое программное ядро под собственным брендом. Система включает backend на Java Spring, пассажирское и водительское приложения на React Native, админку и рабочее место диспетчера на React.

Термин «служба» означает самостоятельного оператора сервиса с собственными клиентами, водителями, приложениями, настройками и финансовыми обязательствами. «Экземпляр» означает изолированную установку платформы для одной службы. «Партнёр» — другая служба, с которой действует соглашение об обмене заказами. «Франчайзер» — владелец сети и центрального контура.

| Маркер | Значение |
| --- | --- |
| B | Утверждённый базис v0.1, обязательный при реализации |
| D | Предложенная детализация в v0.2; не выдаётся за ранее утверждённое решение |
| Q-xx | Открытый вопрос с владельцем решения и моментом, когда ответ необходим |
| M1 | Первая законченная версия одной службы в одном городе |
| M2 | Партнёрский обмен и центральный контур |
| M3 | Развитие после M1/M2 |
| AC-xx | Проверяемый критерий приёмки |
| Н/П | Неприменимо к указанному этапу |

Общее правило: требования B сохраняют силу; детализация D не становится согласованной только потому, что включена в этот файл. Для разработки D используется как предложенная спецификация, а решения, влияющие на финансовые обязательства, публикацию или юридическую модель, закрываются до соответствующего этапа. Реальные ставки, договоры, ключи и персональные данные в ТЗ не включаются.

REQ-GOV-01 [B]. Предыдущие интерфейсы, код и документ Клода — контекст, а не обязательный образец реализации. Архив не прошёл независимую проверку, его пригодность не подтверждена.
REQ-GOV-02 [D]. После утверждения ТЗ единственный актуальный инженерный источник — версия документа и контрактов в репозитории; изменение поведения сопровождается новой записью решения, миграциями и приёмочными проверками.
REQ-GOV-03 [D]. Для каждого требования сохраняется связь с этапом, задачей разработки и проверкой. Формулировки «как в Bolt» не заменяют конкретные правила и не означают копирование чужого интерфейса.

REQ-SCOPE-01 [B]. M1 заканчивается работающим сценарием от приложения до расчёта и поддержки, включая наличную и карточную оплату.
REQ-SCOPE-02 [D]. Конкретные рынок, город, валюту и начальные языки подтвердить в Q-01. Киев/Украина и последующая Польша — контекст исходных материалов, не новое утверждение рынков.
REQ-SCOPE-03 [D]. Безопасная поставка M1 предполагает один backend-артефакт для всех служб и конфигурацию без форков. Разные версии экземпляров допустимы в пределах опубликованного окна совместимости.

AC-01. На чистом окружении развёртывается первая служба, создаётся город и тариф, водитель проходит проверку; заказы из приложения и от диспетчера выполняются до финансового результата.

## 3. Модель службы, города и бренда

REQ-TEN-01 [B]. База, пользователи, секреты, мерчанты, файлы и сотрудники каждой службы изолированы в отдельном экземпляре. Межслужебный доступ возможен только через партнёрские контракты.
REQ-TEN-02 [D]. Экземпляр имеет неизменяемый instance_id; служба — service_id. Во внешних идентификаторах используется пара issuer_instance_id + object_id. Совпадение телефонов в разных службах не объединяет профили.
REQ-TEN-03 [B]. Город определяется точкой подачи. Его конфигурация включает валюту, часовой пояс, рабочие часы, территорию, классы, тарифы и способы оплаты.
REQ-TEN-04 [D]. Пересечение полигонов городов внутри одной службы разрешается только с явным приоритетом. Точка на границе обслуживается по правилу включённой границы; при равном приоритете конфигурация отклоняется.
REQ-TEN-05 [D]. Междугородний маршрут допускается настройкой города подачи. Изменение города после получения цены аннулирует предложение и требует нового расчёта.
REQ-TEN-06 [D]. Изменения города, зон, бренда и тарифов версионируются, проходят проверку и сохраняют автора. Приостановка новых заказов не прерывает действующие поездки.
REQ-TEN-07 [D]. Настройки бренда: имя, логотипы, цвета, контакты поддержки, домен API, app identifiers, политика конфиденциальности и пользовательские условия. Цвета проходят проверку читаемости; бренд не меняет бизнес-правила.
REQ-TEN-08 [D]. У клиента собственные ключи push и учётные записи публикации либо явно согласованная модель владения. Адрес API задаётся доверенной конфигурацией; ввод произвольного сервера пользователем запрещён.

AC-02. Профиль одной службы не доступен по токену другой; изменение тарифа второго города не влияет на согласованный заказ первого. Пограничные и пересекающиеся полигоны дают детерминированный результат.

REQ-AUTH-01 [B]. Роль дополняется ограничением по службе, городам и принадлежности объекта. Проверки выполняются для REST, WebSocket, выгрузок и файлов.
REQ-AUTH-02 [D]. Сотрудники входят через OIDC с обязательным вторым фактором. Keycloak — кандидат реализации, окончательная фиксация в Q-02.
REQ-AUTH-03 [D]. Пассажиры/водители входят по телефону и OTP. Номер нормализуется в E.164. Ответ запроса кода не раскрывает существование профиля.
REQ-AUTH-04 [D]. Предложенные параметры: код 5 минут, 5 попыток, повтор не ранее 60 секунд. Отдельные лимиты по телефону, устройству, IP, стране назначения и общему бюджету отправки. Голосовой код — только после выбора канала и лимитов.
REQ-AUTH-05 [D]. Хранить HMAC кода с серверным секретом, challenge_id, срок и счётчик; не хранить код открыто. Обычный быстрый хэш короткого кода не считать достаточной защитой.
REQ-AUTH-06 [D]. Access token до 15 минут; refresh ротируется. Повторное использование старого refresh отзывает семейство сессии. Для входа сотрудника и высокорисковых операций действуют независимые политики.
REQ-AUTH-07 [D]. Выход/отзыв закрывает связанные push и WS-сессии. Блокировка пользователя запрещает новые операции немедленно; действующая поездка направляется в сопровождение, а не исчезает.
REQ-AUTH-08 [D]. Смена телефона требует подтверждения нового номера и защиты от захвата аккаунта; при потере старого — проверяемый процесс поддержки. Автоматического объединения профилей только по совпадению имени нет.
REQ-AUTH-09 [D]. В мобильном приложении секреты сессии хранятся в защищённом системном хранилище, не в обычном кэше. В web предпочтительна защищённая HttpOnly-сессия/BFF; при bearer-токенах отдельно описываются защита XSS и срок хранения.
REQ-AUTH-10 [D]. Разрешения сотрудников по умолчанию отсутствуют. Возврат, изменение прав и выгрузка чувствительных данных протоколируются.

AC-03. OTP нельзя перебрать повторными challenge; отозванная сессия не принимает оффер; сотрудник другого города не получает заказ ни через прямой URL, ни через подписку WS.

## 5. Приложение пассажира

| Экран | Данные и действия | Пустое/ошибочное состояние |
| --- | --- | --- |
| Вход | Телефон, код, язык, условия и согласия по необходимости | Лимит, неверный код, нет сети |
| Главная | Карта, город, точка подачи, маршрут | Ручной адрес при запрете геолокации |
| Выбор маршрута | A/B, контакт гостя, комментарий, точка входа | Нет результатов, точка вне зоны |
| Предложение | Классы, цена, валюта, ETA, способ оплаты, условия | Нет доступного класса, цена устарела |
| Поиск | Срок поиска, отмена, актуальный этап без технических подробностей | Нет машин, ошибка оплаты |
| Подача | Имя/фото водителя, авто, номер, ETA, связь | Потеря связи с водителем, переназначение |
| Ожидание/поездка | Прибытие, счётчик ожидания, маршрут и поддержка | Устаревшая позиция, спорное начало |
| Результат | Итог и детализация, статус оплаты, оценка | Платёж ожидается, долг, чек ещё формируется |
| История | Список, детали, обращение, квитанция/чек при наличии | Пустая история |
| Профиль | Имя, язык, способы оплаты, приватность, удаление | Требуется повторная авторизация |

REQ-RID-01 [D]. Отказ от геолокации не блокирует ручной заказ. Движение GPS пассажира не меняет вручную зафиксированную точку подачи.
REQ-RID-02 [D]. Перед заказом отображаются обе точки, класс, цена, валюта, способ оплаты, условия ожидания/отмены. Кнопка заказа блокируется до ответа, но защита дублей выполняется сервером.
REQ-RID-03 [B]. До 3 активных заказов на аккаунт плательщика (`active_orders_per_payer`, ADR 0012). В заказе можно указать телефон того, кому заказывают; заказ для гостя относится к аккаунту плательщика и не требует регистрации гостя; ответственность плательщика явно показана.
REQ-RID-04 [D]. ETA является прогнозом. Устаревший прогноз отмечается, отсутствующий не заменяется фиктивным значением.
REQ-RID-05 [D]. При смене исполнителя старый водитель и контакт удаляются из активного экрана, показываются новые данные и причина изменения в допустимой форме.
REQ-RID-06 [D]. Нельзя переключить карту/наличные или маршрут после подтверждения без новой серверной проверки. В M1 маршрут после старта изменяет поддержка по согласованной процедуре; самостоятельное редактирование — M3.
REQ-RID-07 [D]. Отмена показывает подтверждённую сервером возможную плату; при изменении условий между запросом и подтверждением сервер возвращает новый расчёт для подтверждения.
REQ-RID-08 [D]. Оценка 1–5 после завершения, один действующий отзыв на поездку. Период редактирования — конфигурация. Чаевые — отдельная добровольная операция: 10/15/20/25 % с округлением вверх до целой единицы валюты или своя сумма от 1 единицы до стоимости поездки, округлённой вверх (ADR 0012).
REQ-RID-09 [D]. Кнопка связи/безопасности открывает доступные контакты поддержки и местную экстренную связь по выбранному рынку. Не обещать автоматическую отправку экстренным службам без интеграции.
REQ-RID-10 [D]. Удаление аккаунта создаёт запрос с подтверждением личности, а не физически удаляет финансовую историю. Процесс хранения описан в разделе 25.

AC-04. Пассажир без разрешения GPS оформляет поездку вручную; после перезапуска видит тот же заказ; повторное подтверждение не создаёт второй; долг виден отдельно от статуса завершённой поездки.

## 6. Приложение водителя и допуск

REQ-DRV-01 [D]. Профиль: имя, телефон, фото, город допуска, документы и сроки, финансовые реквизиты в необходимом объёме. Автомобиль: марка, модель, цвет, регистрационный номер, год, документы, классы допуска.
REQ-DRV-02 [D]. Статусы проверки: DRAFT → SUBMITTED → UNDER_REVIEW → APPROVED либо CHANGES_REQUIRED/REJECTED. Из APPROVED возможен SUSPENDED. Причина решения обязательна; новые документы не затирают историю.
REQ-DRV-03 [D]. Рабочая сессия привязана к водителю, проверенному автомобилю, городу и устройству. Только одна управляющая сессия устройства на водителя; вход со второго устройства требует контролируемой передачи, а не двух получателей офферов.
REQ-DRV-04 [D]. Выход на линию требует действующего допуска, документов, геолокации и отсутствия блокирующих ограничений. Наличие кассы не становится обязательным без Q-05.
REQ-DRV-05 [D]. Истечение документа во время поездки запрещает новые назначения, но не обрывает текущую. Создаются уведомление и задача проверки.
REQ-DRV-06 [D]. Доступность: OFFLINE, AVAILABLE, PAUSED, BUSY. Связь отдельно: CONNECTED, STALE, DISCONNECTED. Доступность BUSY вычисляется из действующего назначения, не из клиентской кнопки.
REQ-DRV-07 [D]. Приложение показывает маршрут подачи, условия оффера, цену/расчёт заработка с указанием характера суммы, способ оплаты, комментарий и оставшееся серверное время. Таймер телефона не является источником срока.
REQ-DRV-08 [D]. Вкладка «ВСЕМ» доступна только допущенным свободным водителям подходящего города/класса. Удаляет отозванные заказы. До назначения не раскрывает телефон пассажира.
REQ-DRV-09 [D]. Команды «Прибыл», «Начать», «Завершить» доступны только назначенному водителю. Географическое отклонение требует объяснения и проверки; плохой GPS не делает выполнение невозможным без маршрута исключения.
REQ-DRV-10 [D]. Во время поездки сохраняются координаты и очередь команд с client_command_id. Команды исполняются последовательно, показывают pending/confirmed/rejected; недопустимый повтор не считается успехом.
REQ-DRV-11 [D]. Навигация передаёт координаты во внешнее приложение либо использует встроенный маршрут. Внешняя навигация не меняет заказ самостоятельно.
REQ-DRV-12 [D]. Экран заработка отдельно показывает стоимость поездок, комиссию, наличные у водителя, безналичный доход, возвраты, корректировки, задолженность и доступно к выплате. Это разные показатели.
REQ-DRV-13 [D]. Закрытие рабочей сессии во время поездки запрещено; можно отключить получение будущих заказов. Перезапуск приложения восстанавливает текущую сессию.
REQ-DRV-14 [D]. Фоновая геолокация проверяется на реальных iOS/Android, при заблокированном экране и энергосбережении. Нельзя обещать доставку после принудительного завершения приложения ОС/пользователем; сервер обнаруживает потерю свежих данных.

AC-05. Заблокированный водитель не принимает заказ через старую WS-сессию; второй телефон не создаёт вторую управляющую сессию; истёкший документ не прерывает поездку, но блокирует следующее назначение.

## 7. Диспетчер и колл-центр

REQ-OPS-01 [D]. Рабочий экран содержит входящий звонок/ручной номер, поиск клиента, маршрут, расчёт цены, создание заказа, текущие заказы, свободные машины и очередь проблем. Операции доступны с клавиатуры; незавершённая форма не теряется при входящем звонке.
REQ-OPS-02 [D]. Заказ может иметь заказчика, плательщика и получателя поездки. Телефон гостя хранится как контакт заказа с ограниченным доступом; служебное создание контакта не означает подтверждённый вход этого человека.
REQ-OPS-03 [D]. Заказ от диспетчера содержит created_by_employee_id, канал PHONE, основание/звонок, историю правок. Цена и ограничения проверяются тем же backend, что у пассажира.
REQ-OPS-04 [B]. Ручное предложение не обходит подтверждение водителя, допуск, сроки и защиту от двойного назначения.
REQ-OPS-05 [D]. Переназначение до старта требует причины и завершения старого назначения. При IN_SERVICE обычное переназначение запрещено: требуется процедура прерывания и новый связанный заказ.
REQ-OPS-06 [D]. Очередь проблем: нет водителя, потеря связи после назначения, спорное прибытие, ошибка оплаты, незавершённый платёжный результат, конфликт партнёра. Задача имеет владельца, приоритет, срок реакции и журнал.
REQ-OPS-07 [D]. Авария телефонии не блокирует ручной ввод и существующие заказы. Нельзя автоматически создавать два заказа из двух событий одного звонка.
REQ-OPS-08 [D]. Asterisk-интеграция включает SIP/WebRTC, очереди, удержание, перевод, исходящий звонок, состояние оператора, card-pop. ARI/AMI и выбор библиотеки уточняются техническим прототипом.
REQ-OPS-09 [D]. Запись звонка включается только по согласованной политике рынка. Запись хранится отдельно с ограничением доступа; её ссылка не является публичной. Подменные номера — отдельная опция после выбора SIP-провайдера.
REQ-OPS-10 [D]. Обрыв звонка не отменяет заказ. Событие звонка и поездка связаны, но имеют независимые жизненные циклы.

AC-06. При падении Asterisk диспетчер создаёт ручной заказ, а после восстановления звонок не порождает дубль. Переназначение занятому водителю отклоняется общим ядром.

## 8. Админка, поддержка и финансы

REQ-ADM-01 [D]. Разделы: обзор, заказы/поездки, live-карта, водители/автомобили/документы, пассажиры, обращения, города/зоны/классы, тарифы, адреса, финансы, интеграции, сотрудники/права, аудит; партнёры и франшиза появляются в M2.
REQ-ADM-02 [D]. Карточка заказа показывает временную шкалу всех попыток назначения, событий поездки, цены, оплаты и действий сотрудников. Записи о факте не редактируются через форму.
REQ-ADM-03 [D]. Коррекция выполняется отдельной командой с причиной и ссылкой на исходный факт. Изменить driver_id или сумму прямой правкой строки в админке нельзя.
REQ-ADM-04 [D]. Массовые операции показывают предварительный объём, требуют отдельного разрешения, выполняются фоном с результатом по каждой записи. Блокировка не должна случайно завершать активные поездки.
REQ-ADM-05 [D]. Возврат проходит состояния REQUESTED → APPROVED → PROCESSING → SUCCEEDED/FAILED/UNKNOWN. Лимит сотрудника и необходимость второго согласующего настраиваются; числа — Q-06.
REQ-ADM-06 [D]. Отчёты содержат часовой пояс, период, валюту, фильтры и время формирования. Суммы разных валют не складываются без явной конвертации; конвертация в M1 не поддерживается.
REQ-ADM-07 [D]. Выгрузки выполняются фоновыми заданиями, требуют повторной проверки прав при скачивании и имеют ограниченный срок ссылки. Экспорт защищён от формул при открытии CSV.
REQ-ADM-08 [D]. Live-карта фильтруется по городу, классу, состоянию и свежести. Детальный поток виден только для выбранной области; не рассылать все GPS-точки каждому сотруднику.
REQ-ADM-09 [D]. Обращение содержит категорию, поездку, участников, владельца, сообщения, вложения и решение. Внутренние комментарии не попадают пассажиру.
REQ-ADM-10 [D]. Изменения мерчантов, маршрутизации денег и прав требуют усиленной проверки, скрытия секретов и аудита. Кнопка «проверить соединение» не выводит ключи в браузер.

AC-07. Возврат выше лимита нельзя провести прямым API-запросом; экспорт не раскрывает другой город; исходная финансовая запись сохраняется после корректировки.

## 9. Состояния заказа

Все таблицы переходов далее — D, предложенная спецификация. Неуказанные переходы запрещены. Любое изменение проверяет ожидаемую версию и записывает actor, command_id, reason, correlation_id и серверное время.

| Статус | Значение |
| --- | --- |
| AWAITING_PAYMENT | Заказ создан, ожидается обязательная авторизация карты |
| READY | Финансовая предпосылка выполнена или выбраны наличные; поиск ещё не запущен |
| SEARCHING | Есть активная попытка поиска, исполнителя нет |
| ASSIGNED | Назначение подтверждено, водитель следует к пассажиру/ожидает |
| IN_SERVICE | Перевозка началась |
| FULFILLED | Перевозка завершена; оплата может быть не завершена |
| CANCELLED | Заказ прекращён по инициативе участника/поддержки |
| UNFULFILLED | Выполнение не началось из-за отсутствия исполнителя или невыполненной предпосылки |

| Переход | Инициатор | Предусловия и результат |
| --- | --- | --- |
| Создание → AWAITING_PAYMENT | Пассажир/диспетчер | Карта, действующий quote; заказ и платёжное намерение записаны до внешнего вызова |
| Создание → READY | Пассажир/диспетчер | Наличные разрешены; действующий quote |
| AWAITING_PAYMENT → READY | Финансы | Подтверждён достаточный холд; заказ не отменён |
| AWAITING_PAYMENT → UNFULFILLED | Система | Достоверный отказ/истечение срока; при UNKNOWN сначала сверка |
| READY → SEARCHING | Система | Город принимает заказы; dispatch_attempt создан |
| SEARCHING → ASSIGNED | Ядро | Атомарное подтверждение назначения |
| ASSIGNED → SEARCHING | Ядро | Старое назначение окончательно освобождено до старта; пассажир не отменил |
| ASSIGNED → IN_SERVICE | Назначенный водитель | Прибытие/исключение, действующее назначение |
| IN_SERVICE → FULFILLED | Назначенный водитель | Зафиксированы завершение, расчётный факт и событие для оплаты |
| SEARCHING → UNFULFILLED | Система | Истёк общий deadline, нет действующего/неопределённого назначения |
| До IN_SERVICE → CANCELLED | Уполномоченный участник | Правила отмены, освобождение назначения и обработка холда |
| IN_SERVICE → CANCELLED | Поддержка | Исключительное прерывание с причиной, фактом частичного исполнения и отдельным расчётом |

REQ-ORD-01 [D]. Форма до подтверждения не является заказом. READY может быть кратковременным состоянием, но его факт фиксируется.
REQ-ORD-02 [D]. FULFILLED/CANCELLED/UNFULFILLED — терминальные статусы. Повторное выполнение создаёт новый связанный заказ, не «открывает» старый.
REQ-ORD-03 [D]. Поиск MATCHING/BROADCAST/PARTNER является состоянием dispatch_attempt, а не дополнительным статусом жизненного цикла заказа.
REQ-ORD-04 [D]. Итог FULFILLED не означает PAID; CANCELLED не означает отсутствие платы за отмену.
REQ-ORD-05 [D]. При завершении без связи клиент показывает «отправка завершения», пока сервер не подтвердит. Принятый факт окончания хранит reported_at и recorded_at; подозрительное время требует проверки.
REQ-ORD-06 [D]. Если GPS отсутствует, завершение всё равно можно заявить; качество данных отражается в расчёте/проверке. Автоматическое начисление произвольного пробега запрещено.

AC-08. Все разрешённые переходы покрыты сценариями; запрещённые дают STATE_CONFLICT без частичных изменений. Одновременные принятие/отмена приводят к одному допустимому порядку, без двух исполнителей.

## 10. Предложения, назначения, поездки и рабочие сессии

| Сущность | Статусы | Основное правило |
| --- | --- | --- |
| offer | OPEN, ACCEPTED, REJECTED, EXPIRED, REVOKED | OFFER не равен назначению; принять можно только OPEN до expires_at |
| assignment | RESERVED, COMMITTED, RELEASED, REVOKED, COMPLETED | RESERVED/COMMITTED удерживают исполнителя и заказ |
| trip | TO_PICKUP, WAITING, IN_PROGRESS, COMPLETED, ABORTED | Поездка относится к одному назначению; новая попытка — новая trip |
| work_session | OPEN, CLOSING, CLOSED | Открытая сессия содержит режим приёма заказов и устройство |
| dispatch_attempt | PERSONAL, BROADCAST, PARTNER, STOPPED, EXHAUSTED | Сроки и этапы переживают рестарт |

REQ-ASG-01 [D]. Для локального назначения ядро может создать сразу COMMITTED; RESERVED предназначен для подтверждаемого межслужебного резервирования.
REQ-ASG-02 [D]. Предложение отмечается ACCEPTED только в успешной транзакции назначения. Позднее принятие получает OFFER_EXPIRED/OFFER_REVOKED, а не молчаливый успех.
REQ-ASG-03 [D]. При COMMITTED создаётся trip TO_PICKUP. Прибытие переводит TO_PICKUP → WAITING; старт WAITING → IN_PROGRESS; завершение IN_PROGRESS → COMPLETED.
REQ-ASG-04 [D]. До старта отмена или переназначение переводит trip в ABORTED и освобождает assignment. После старта обычное освобождение запрещено; прерывание выполняет поддержка.
REQ-ASG-05 [D]. Начало без подтверждённого прибытия возможно только как явно разрешённое исключение с причиной; финальные проверки и аудит сохраняются.
REQ-ASG-06 [D]. Прибытие проверяет расстояние до точки подачи, свежесть и точность GPS. Предложенные границы: 150 м и точка не старше 15 секунд; исключение — ручное подтверждение с причиной. Числа калибруются пилотом.
REQ-ASG-07 [D]. WAITING фиксирует серверное arrived_at, бесплатный лимит и тариф ожидания. Участник видит один и тот же источник времени; потеря WS не обнуляет ожидание.
REQ-ASG-08 [D]. На локальном ядре порядок блокировок единый: order → driver capacity → assignment/offer. Блокировка водительской ёмкости сохраняется до окончания/освобождения назначения.
REQ-ASG-09 [D]. Предикат частичного уникального индекса использует статусы RESERVED/COMMITTED, а не now(). Истёкший резерв освобождается явной транзакцией. Уникальные индексы по order_id и локальному driver_id защищают инварианты.
REQ-ASG-10 [D]. Для внешнего водителя в экземпляре инициатора хранится partner_driver_ref, локальный driver_id отсутствует. Локальную ёмкость блокирует экземпляр исполнителя. Межэкземплярная уникальность обеспечивается протоколом, не локальным индексом.
REQ-ASG-11 [D]. Совпадение человека в независимых службах не создаёт глобальную блокировку: единая идентификация водителя между службами не входит в базис. Это ограничение явно учитывать при партнёрских соглашениях.

AC-09. При 100 конкурентных принятиях одного заказа возникает одно назначение. При двух конкурентных заказах одному локальному водителю подтверждается одно. Перезапуск не освобождает действующее назначение.

## 11. Диспетчеризация и вкладка «ВСЕМ»

REQ-DSP-01 [D]. Кандидат должен иметь допуск в городе, подходящий автомобиль/класс, открытую рабочую сессию, свежую позицию, разрешённый способ оплаты и свободную ёмкость в PostgreSQL.
REQ-DSP-02 [D]. Redis GEO формирует предварительный список; окончательные условия проверяются при назначении. TTL отдельного state не удаляет автоматически участника GEO: нужен очиститель и повторный фильтр свежести.
REQ-DSP-03 [D]. Стартовые параметры: радиусы 2 и 5 км, до 20 кандидатов, дорожный ETA до 10 кандидатов; персональный оффер 15 секунд, общий этап до 60 секунд, общий поиск до 180 секунд. Это калибруемые параметры, не обещание качества.
REQ-DSP-04 [D]. Скоринг учитывает ETA, простой и документированные ограничения. Коэффициенты фиксируются версией, отказ конкретного водителя не должен запускать повтор одного и того же оффера без новой попытки.
REQ-DSP-05 [D]. M1 использует один персональный оффер на заказ и один активный персональный оффер на водителя. Ограничение офферов сохраняется в PostgreSQL; Redis может ускорять предварительное резервирование.
REQ-DSP-06 [D]. При переходе к «ВСЕМ» открытый персональный оффер отзывается атомарно со сменой этапа. Задача таймера содержит attempt_id и generation, устаревшая задача ничего не меняет.
REQ-DSP-07 [D]. «ВСЕМ» фильтруется по городу, зоне, классу, оплате и допуску. Вход/освобождение водителя вызывает запрос снимка, не только ожидание следующего push.
REQ-DSP-08 [D]. При партнёрском предложении заказ может оставаться во «ВСЕМ», но начало резервирования партнёра и локальное принятие конкурируют в одном ядре инициатора.
REQ-DSP-09 [D]. Несколько worker обрабатывают deadline безопасно через блокировки/lease. Сроки находятся в базе; после падения worker просроченные задачи подбираются другим.
REQ-DSP-10 [D]. Ручной оффер использует общий deadline; диспетчер не может бесконечно продлевать поиск без нового подтверждения пассажира и проверки холда.
REQ-DSP-11 [D]. При отсутствии маршрутизатора расширенный перебор кандидатов ограничен; система не создаёт неограниченный поток запросов или офферов.
REQ-DSP-12 [D]. Сохраняются причина исключения кандидата, результат оффера, время первого оффера, назначения, перехода этапов и исчерпания. Не хранить избыточные персональные данные в метриках.

AC-10. После полной потери Redis нет двойных назначений; индексы восстанавливаются по свежим позициям, таймеры — из PostgreSQL. Просроченный worker не отменяет уже принятый заказ.

## 12. Полная модель состояний водителя

Единого поля driver_status недостаточно. Состояние водителя — сочетание допуска, рабочей сессии, намерения получать заказы, связи и занятости. Клиент показывает понятное итоговое состояние; backend проверяет каждую составляющую.

### 12.1 Независимые оси состояния

| Ось | Статусы | Источник |
| --- | --- | --- |
| Учётная запись | ACTIVE, BLOCKED, DELETION_PENDING, ANONYMIZED | Доступ |
| Допуск | NOT_SUBMITTED, IN_REVIEW, CHANGES_REQUIRED, APPROVED, REJECTED, SUSPENDED, EXPIRED | Документы и проверка |
| Автомобиль | DRAFT, IN_REVIEW, APPROVED, SUSPENDED, EXPIRED | Карточка автомобиля и документы |
| Рабочая сессия | OPEN, CLOSING, CLOSED | PostgreSQL |
| Намерение | ACCEPTING, PAUSE_AFTER_CURRENT, NOT_ACCEPTING | Команда водителя и правила |
| Связь | CONNECTED, STALE, DISCONNECTED | Серверное время последнего heartbeat |
| Геолокация | FRESH, STALE, INVALID, UNAVAILABLE | Последняя допустимая GPS-точка |
| Занятость | FREE, OFFERED, RESERVED, TO_PICKUP, WAITING, ON_TRIP | Оффер, назначение и поездка |
| Финансовое ограничение | CLEAR, WARNING, RESTRICTED | Версионированная политика задолженности |

REQ-DS-01 [D]. Оси BLOCKED/SUSPENDED/RESTRICTED запрещают новые назначения, но не переводят автоматически ON_TRIP в FREE. Завершение и обращения по действующей поездке остаются доступны в ограниченной сессии.
REQ-DS-02 [D]. Предложенный признак ONLINE означает открытую сессию и намерение работать; пригодность для нового заказа определяется отдельным eligibility. Не считать ONLINE синонимом AVAILABLE.
REQ-DS-03 [D]. После stale/disconnected водитель исчезает из кандидатов, но действующее назначение сохраняется. На карте поддержки отображается время последней связи.
REQ-DS-04 [D]. Heartbeat без свежих координат восстанавливает CONNECTED, но не FRESH и не eligibility.
REQ-DS-05 [D]. OFFERED ограничивает другие персональные предложения. При истечении оффера возвращается FREE только если нет назначения. Мобильный таймер не освобождает ёмкость.
REQ-DS-06 [D]. Автомобиль меняется только вне действующего оффера/резерва/назначения, через проверку допуска. Новый город рабочей сессии требует повторной проверки.
REQ-DS-07 [D]. Выход за полигон не отменяет поездку. Возможность получать новые заказы определяется свежей точкой подачи кандидата и настройкой зоны возврата.
REQ-DS-08 [D]. Подозрение GPS-spoofing создаёт риск-флаг и проверку. Не завершать поездку и не штрафовать автоматически одним скачком GPS.

### 12.2 Переходы водителя

| Событие | Из | В | Условия и побочные действия |
| --- | --- | --- | --- |
| Подать документы | NOT_SUBMITTED/CHANGES_REQUIRED | IN_REVIEW | Обязательные поля/файлы прошли проверку |
| Подтвердить проверку | IN_REVIEW | APPROVED | Сотрудник с правом; даты и классы допущены |
| Запросить исправления | IN_REVIEW | CHANGES_REQUIRED | Причина и список документов |
| Приостановить | APPROVED | SUSPENDED | Причина, срок/условия; запрет новых заказов |
| Истёк документ | APPROVED | EXPIRED | Плановая проверка по серверной дате рынка |
| Выйти на линию | CLOSED | OPEN + ACCEPTING | Допуск и автомобиль действуют, связь/позиция пригодны |
| Получить оффер | FREE | OFFERED | eligibility повторно проверен |
| Отклонить/истечение | OFFERED | FREE | Нет другого действующего резерва/назначения |
| Принять локально | FREE/OFFERED | TO_PICKUP | Транзакционное подтверждение назначения |
| Резерв партнёра | FREE/OFFERED | RESERVED | Протокол M2 и блокировка водительской ёмкости |
| Подтвердить резерв | RESERVED | TO_PICKUP | Достоверное COMMIT, актуальный generation |
| Прибыть | TO_PICKUP | WAITING | Геопроверка или разрешённое исключение |
| Начать | WAITING | ON_TRIP | Активное назначение и допустимый порядок команд |
| Завершить | ON_TRIP | FREE либо NOT_ACCEPTING | Trip завершена и назначение освобождено одной транзакцией |
| Пауза | FREE | NOT_ACCEPTING | Открытые офферы отозваны |
| Пауза во время поездки | TO_PICKUP/WAITING/ON_TRIP | Та же занятость + PAUSE_AFTER_CURRENT | Следующее назначение запрещено |
| Возобновить | NOT_ACCEPTING | FREE + ACCEPTING | Повторная проверка eligibility |
| Выйти | FREE/NOT_ACCEPTING | CLOSED | Нет резерва и назначения; офферы отозваны |
| Запросить выход занятым | TO_PICKUP/WAITING/ON_TRIP | CLOSING + PAUSE_AFTER_CURRENT | Сессия закроется после освобождения |
| Потерять сеть | Любая занятость | Та же занятость + DISCONNECTED | Исключение из нового подбора, уведомление при активной поездке |
| Восстановить сеть | DISCONNECTED | CONNECTED | Проверка сессии, свежей точки и серверного снимка |
| Отозвать водителя до старта | TO_PICKUP/WAITING | FREE/NOT_ACCEPTING | Старое назначение закрыто; заказ ищет нового исполнителя или отменён |

REQ-DS-09 [D]. Потерянный ответ на «Принять» требует запроса результата command_id; водитель не видит «заказ не принят» только по таймауту HTTP.
REQ-DS-10 [D]. Когда водитель уже TO_PICKUP/WAITING/ON_TRIP, приложение не принимает второй оффер. Защита backend обязательна даже при ошибке приложения.
REQ-DS-11 [D]. Клиент не передаёт произвольный новый статус; он отправляет разрешённую команду. Нельзя выполнить PATCH driver.status=FREE.
REQ-DS-12 [D]. После завершения водитель может брать новый заказ, даже если карточный платёж пассажира ещё сверяется; финансовая политика может ограничить новые назначения только отдельным явным решением.
REQ-DS-13 [D]. Спор «пассажир не платил наличными» не исправляется переводом поездки обратно в ON_TRIP. Открывается обращение и финансовый спор.

AC-11. Для каждой строки переходов проверяются позитивный сценарий, запрещённый инициатор, повтор команды и конфликт версии. DISCONNECTED + ON_TRIP никогда не попадает в список свободных.

## 13. Отмена, неявка, переназначение и исключения

| Ситуация | Кто может инициировать | Решение | Деньги и уведомления |
| --- | --- | --- | --- |
| Пассажир отменил до назначения | Плательщик/уполномоченный диспетчер | CANCELLED, остановить поиск/офферы | В базовом предложении бесплатно; снять холд |
| Пассажир отменил после назначения | Плательщик | CANCELLED после расчёта условий | Плата по подтверждённой политике; уведомить водителя |
| Пассажир отменил после прибытия | Плательщик | CANCELLED, зафиксировать ожидание | Рассчитать отмену/ожидание без двойного начисления |
| Водитель отказался до старта | Назначенный водитель | Закрыть назначение, предложить повторный поиск | Не начислять пассажиру плату за отказ водителя |
| Водитель пропал до старта | Система/диспетчер | Задача связи; проверка и переназначение по политике | Не назначать второго, пока старое назначение не закрыто |
| Пассажир не вышел | Водитель | Заявка no-show после минимального ожидания и попытки связи | Плата только при выполнении условий; спор доступен |
| Нет машин | Система | UNFULFILLED после deadline | Освобождение холда, предложение повторного заказа |

| Поломка после старта | Водитель/поддержка | Прервать поездку, связанный новый заказ при необходимости | Отдельно согласованный частичный расчёт |
| Пассажир просит выйти | Пассажир/водитель | Безопасно завершить фактический маршрут | Расчёт по разрешённым условиям; спор при расхождении |
| Водитель нажал старт ошибочно | Поддержка | Аудируемое исправление факта, без удаления истории | Блокировать ошибочное списание до проверки |
| Угроза безопасности | Участник/поддержка | Приоритетная задача, доступные контакты помощи | Не выполнять автоматическое спорное начисление |
| Позднее подтверждение после отмены | Система | Сохранить отмену, отклонить назначение | Поздний холд отменить/вернуть по статусу |
| Изменились точки после quote | Пассажир/диспетчер до заказа | Новый quote | Старый не используется |

REQ-CAN-01 [D]. reason_code выбирается из справочника по актору и этапу; свободный комментарий дополняет, но не заменяет код. Причина пользователю и внутренняя причина могут отличаться по уровню доступа.
REQ-CAN-02 [D]. Порог бесплатной отмены, минимальное ожидание no-show и плата — версия политики города, согласованная в Q-07. До её настройки платные отмены выключены.
REQ-CAN-03 [D]. Непосредственно перед платной отменой выдаётся cancellation_quote с expires_at и order_version. Смена водителя/этапа требует повторной проверки. При отсутствии сети платная отмена остаётся ожидающей, а не считается завершённой локально.
REQ-CAN-04 [D]. Плата за ожидание не начисляется до достоверного прибытия. Ложное прибытие, недоступная точка и некачественные координаты направляются на проверку.
REQ-CAN-05 [D]. Отказ водителя запускает новый dispatch_attempt и сохраняет историю старого. Общий срок ожидания пассажира не сбрасывается незаметно; продление требует показанного согласия.
REQ-CAN-06 [D]. No-show фиксирует arrived_at, попытки связи и фактическую длительность ожидания. GPS сам по себе не доказывает неявку.
REQ-CAN-07 [D]. После начала все исключительные действия требуют отдельного разрешения. Задним числом менять времена можно только корректирующей записью с причиной и автором.
REQ-CAN-08 [D]. Отмена и успешное начало сериализуются: если начало выиграло транзакцию, обычная отмена отклоняется и предлагается обращение; если отмена выиграла, старт отклоняется.

AC-12. Одновременные отмена и старт не приводят к отменённому заказу с продолжающейся обычной поездкой. Ложное no-show не списывает плату без обязательных условий.

## 14. География, GPS, маршруты и адреса

REQ-GEO-01 [D]. Координаты WGS84, широта/долгота валидируются; в геометрии x=longitude, y=latitude. Хранить recorded_at, received_at, accuracy, speed, heading, session_id и sequence.
REQ-GEO-02 [D]. Текущая позиция обновляется только более новым допустимым sequence для текущей сессии. Старые буферизованные точки пишутся в трек, но не перемещают текущую машину назад.
REQ-GEO-03 [D]. Предложенная частота: 3–5 секунд на линии, 2–3 секунды при подаче/поездке; при неподвижности адаптивно. Значения зависят от ОС, батареи и пилота.
REQ-GEO-04 [D]. Предложенные пороги: STALE после 15 секунд без heartbeat, DISCONNECTED после 30; eligibility требует GPS не старше 15 секунд с допустимой точностью. Эти значения настраиваются и не освобождают занятого водителя.
REQ-GEO-05 [D]. Поток GPS имеет backpressure, лимит пакетной загрузки и дедупликацию. Сервер не принимает пакет неограниченного размера. Локальный буфер зашифрован, ограничен объёмом/временем и очищается после подтверждения.
REQ-GEO-06 [D]. GPS с будущим временем, невозможным скачком или плохой точностью помечается/отклоняется по политике. Сырой трек и очищенный результат различаются, подозрительная точка не используется для автоматической доплаты.
REQ-GEO-07 [D]. Маршрутизатор и геокодер подключены через разные интерфейсы. GraphHopper — кандидат маршрутизации; конкретная версия и профили фиксируются после прототипа. Дорожный ETA без информации о пробках не заявляется как точный.
REQ-GEO-08 [D]. Отказ маршрутизатора: повтор в пределах бюджета, затем отказ выдачи фиксированной цены либо явно обозначенная оценка по согласованной политике. Нельзя молча выдать цену по прямой за точную стоимость.
REQ-GEO-09 [D]. Подложка карты и геокодер — отдельные поставщики/лицензии. Выбор MapLibre или другого SDK проверяется совместно с условиями источника данных.
REQ-GEO-10 [D]. Собственный адрес содержит id, город, тип HOUSE/PLACE/ENTRANCE, подпись, язык, алиасы, улицу/дом при наличии, точку подачи, инструкции, источник, active/hidden, version.
REQ-GEO-11 [D]. Адрес провайдера имеет provider/object_id, лицензионную метку и срок хранения. Срок не назначается произвольно. Решение Q-08 (ADR 0012): результаты Google и Visicom не сохраняются; встроенный справочник адресов службы хранится и редактируется; повторные адреса берутся из истории заказов клиента.
REQ-GEO-12 [D]. Исправление провайдерского адреса создаёт собственную запись и связь override. Не копировать провайдерскую базу под видом собственных адресов; происхождение и допустимость каждого поля сохраняются.
REQ-GEO-13 [D]. Приоритет поиска: свои разрешённые адреса → допустимый кэш → провайдеры по конфигурации. Мультиязычные алиасы и домовые суффиксы нормализуются без потери различий 2/26/2А/2-А/корпус.
REQ-GEO-14 [D]. Дедупликация учитывает provider_id, город, дом/корпус и координаты. Близость 25 м сама по себе не доказывает одинаковый вход; точка подачи и почтовый адрес различаются.
REQ-GEO-15 [D]. Изменение/скрытие/восстановление — с оптимистичной блокировкой, причиной и историей. Выбор скрытого адреса из старого кэша требует новой проверки.
REQ-GEO-16 [D]. Для подсказок: debounce около 300 мс, минимум 3 символа, отмена устаревших запросов, ограничение результата и rate limit. Пустой ответ провайдера не означает постоянное отсутствие адреса.
REQ-GEO-17 [D]. Импорт OSM — отдельное задание с версией источника, лицензией, предварительным просмотром, dry run, отчётом дублей и откатом импортированной партии. Не перезаписывать ручные правки.
REQ-GEO-18 [D]. Выбор города на границе использует покрытие границы и явный приоритет; невалидный полигон нельзя публиковать.

AC-13. Буфер GPS за 10 минут не перемещает текущую машину назад; «дом 2» не становится «дом 26»; скрытие переживает разрешённое обновление кэша; два разных входа не сливаются по близости.

## 15. Тарифы, предложение цены и окончательный расчёт

REQ-PRC-01 [D]. Тариф версионируется по городу/классу/валюте и effective_from. Черновик, публикация и архив разделены. Пересекающиеся активные версии отклоняются.
REQ-PRC-02 [D]. Состав: базовая подача, цена расстояния, цена времени, минимум, бесплатное ожидание, платное ожидание, вне зоны, разрешённые сборы, отмена, комиссия. Все денежные суммы — целые минимальные единицы; коэффициенты — точные decimal/rational.
REQ-PRC-03 [D]. Предложенная формула: round_half_up(max(minimum, pickup + distance_component + duration_component) × demand_factor) + approved_fees. Правила округления каждой компоненты и итогов фиксируются одной версией; ожидание/отмена рассчитываются отдельно.
REQ-PRC-04 [D]. В M1 demand_factor=1. Динамический коэффициент включается после отдельного согласования и тестирования; он фиксируется в quote и не меняется во время поиска.
REQ-PRC-05 [D]. Quote содержит маршрут/точки, город, класс, цену, валюту, tariff_version, pricing_policy_version, компоненты, expires_at, payment constraints и fingerprint запроса. Предложенный срок 5 минут.
REQ-PRC-06 [D]. Quote привязан к инициатору и используется для одного заказа. Проверка и потребление атомарны; повтор той же команды возвращает исходный заказ. Сервер не принимает сумму от клиента как истину.
REQ-PRC-07 [D]. После создания заказа срок исходного quote не отменяет принятую цену. Продление общего поиска и существенное изменение условий требуют явно согласованной процедуры нового предложения.
REQ-PRC-08 [D]. Отклонение GPS/маршрута — повод проверить, а не автоматически повысить цену на 20%. Доплата разрешена только опубликованным правилом, согласием на изменение или аудируемым разрешением по спору.
REQ-PRC-09 [D]. Ожидание считается по серверным фактам; предложено посекундное начисление после бесплатного лимита с финальным округлением. Политика округления ожидания — Q-07.
REQ-PRC-10 [D]. Итоговый расчёт имеет version и breakdown. Финансовый posting использует конкретную final_fare_version; последующая коррекция создаёт дельту, а не перезаписывает старую сумму.
REQ-PRC-11 [D]. При неполном треке действует опубликованная fallback-политика: исходная цена плюс только доказанные согласованные изменения; спорные компоненты не списываются автоматически.
REQ-PRC-12 [D]. Комиссия хранится снимком условий на заказ/назначение, а не текущим процентом администратора на момент просмотра отчёта.

Пример проверки арифметики: подача 2 000, расстояние 7 500, время 1 500, минимум 5 000, коэффициент 1 дают 11 000 минимальных единиц до разрешённых сборов. Это синтетический пример, не тариф и не конкретная валюта.

AC-14. Изменение опубликованного тарифа не меняет старый заказ. Повтор финализации даёт тот же расчёт. Неполный трек не создаёт случайную доплату.

## 16. Платежи, карта, наличные и долг

### 16.1 Разделение сущностей

payment_intent — обязательство оплатить конкретное основание и сумму; payment_operation — отдельная внешняя операция AUTH/CAPTURE/VOID/CHARGE/REFUND; payment_event — сообщение провайдера; settlement — результат погашения; debt — непогашенный остаток обязательства.

Технический timeout не равен отказу. Статус UNKNOWN означает неизвестный результат внешней операции и требует сверки перед повторным списанием.

| Состояние оплаты | Значение | Допустимое продолжение |
| --- | --- | --- |
| NOT_REQUIRED | Бесплатная операция/нет обязательства | Новое основание при корректировке |
| AUTH_PENDING | Запрошен холд | AUTHORIZED, DECLINED, UNKNOWN |
| AUTHORIZED | Средства заблокированы | CAPTURE_PENDING, VOID_PENDING, EXPIRED |
| CAPTURE_PENDING | Отправлено списание | PAID, PARTIALLY_PAID, DECLINED, UNKNOWN |
| PAYMENT_PENDING | Ожидание обычной оплаты/ссылки/доплаты | PAID, PARTIALLY_PAID, FAILED, UNKNOWN |
| CASH_EXPECTED | Ожидается наличная оплата | CASH_REPORTED, DISPUTED |
| CASH_REPORTED | Водитель сообщил получение | Финансовый учёт; спор создаётся отдельно |
| PARTIALLY_PAID | Погашена только часть | Доплата/долг/проверка |
| PAID | Обязательство погашено | Возврат или chargeback отдельной сущностью |
| VOID_PENDING | Запрошено освобождение холда | VOIDED, UNKNOWN |
| VOIDED / EXPIRED | Холд снят/истёк | Новая авторизация по правилам |
| DECLINED / FAILED | Подтверждён отказ | Новая разрешённая попытка |
| UNKNOWN | Результат не установлен | Проверка статуса/ручная сверка |
| DISPUTED | Спор по наличным/платежу | Решение с корректировками |

Это агрегированные отображаемые статусы. Состояние отдельной операции не должно перезаписывать результаты других операций: у одной поездки могут одновременно быть PAID, частичный возврат и открытый спор.

### 16.2 Карта: предлагаемое решение M1

REQ-PAY-01 [D]. Выбранная для проекта ТЗ схема: авторизовать сумму до запуска поиска. Создать заказ AWAITING_PAYMENT и payment_intent локально, затем выполнить внешний AUTH вне транзакции. Только достоверный успех переводит заказ в READY/SEARCHING. Решение подлежит утверждению в Q-09.
REQ-PAY-02 [D]. Время ожидания AUTH ограничено пользовательским deadline. При UNKNOWN поиск не начинается, выполняется сверка; отмена заказа разрешена, а поздний успех AUTH запускает VOID вместо поиска.
REQ-PAY-03 [D]. Холд = согласованная цена; дополнительный резерв по умолчанию 0 до Q-09. Возможность резерва, повторной авторизации, доплаты и SCA проверяется для конкретного мерчанта/рынка.
REQ-PAY-04 [D]. Завершение поездки записывает факт, final_fare и задачу списания. Внешний CAPTURE выполняется асинхронно; водитель освобождается после подтверждения факта ядром, а не после ответа банка.
REQ-PAY-05 [D]. При финале ниже холда списывается разрешённая сумма, остаток освобождается по возможностям провайдера. При финале выше холда дополнительная сумма проходит отдельную согласованную операцию/подтверждение; молчаливого неограниченного списания нет.
REQ-PAY-06 [D]. При отмене без платы снять холд; с подтверждённой платой списать разрешённую часть и освободить остаток. Если результат назначения/отмены неопределён у партнёра, финансовое решение ждёт согласования фактов.
REQ-PAY-07 [D]. Истечение холда во время долгой поездки создаёт задачу повторной авторизации или alternative payment по согласованной политике. Нельзя бесконечно повторять запросы или прерывать физическую перевозку.
REQ-PAY-08 [D]. Токен карты привязан к провайдеру, мерчанту и владельцу. При смене мерчанта токен не переносится без документированной поддержки. В приложение/логи не попадают PAN/CVV.
REQ-PAY-09 [D]. WayForPay — кандидат первого адаптера из исходных материалов. Наличие операций AUTH/Settle/Refund/CheckStatus подтверждается документацией; доступность токенизации, выплат, валют и конкретных сценариев должна быть подтверждена договором и sandbox-проверкой.
REQ-PAY-10 [D]. Каждый запрос провайдеру получает стабильную ссылку и локальный operation_id. Автоповтор разрешён только при известной идемпотентности либо после CheckStatus; новый reference при сетевом timeout не создаётся автоматически.
REQ-PAY-11 [D]. Входящий callback проверяет подпись по схеме провайдера, мерчанта и допустимость перехода. Сохраняется inbox до подтверждения приёма. Дедупликация по event_id либо устойчивому сочетанию provider/merchant/reference/type/status и fingerprint; один reference сам по себе не отбрасывает последующие статусы.
REQ-PAY-12 [D]. Webhook не доверяет клиентской сумме и не меняет чужой payment. Проверяются валюта, ожидаемая сумма/пределы, мерчант и ссылка.
REQ-PAY-13 [D]. Старое событие не откатывает PAID в PENDING. Неоднозначность разрешается запросом провайдеру и сверкой, а не временем прихода callback.
REQ-PAY-14 [D]. Ручной повтор операции возможен только с проверкой результата прежней и отдельным правом. История сохраняет инициатора.

### 16.3 Наличные, ссылки и задолженность

REQ-PAY-15 [D]. На завершении водитель сообщает CASH_RECEIVED либо CASH_NOT_RECEIVED. Это заявление, а не независимое доказательство оплаты. Пассажир может оспорить; финансовые изменения выполняются через решение спора.
REQ-PAY-16 [D]. При наличных комиссия образует обязательство водителя перед службой. Предел долга и политика запрета новых назначений задаются отдельно; активная поездка не отменяется.
REQ-PAY-17 [D]. Телефонный заказ оплачивается наличными либо по ссылке после выбора мерчанта. Ссылка имеет срок и токен, не раскрывает телефон/полный маршрут и не передаёт реквизиты банковской карты платформе.
REQ-PAY-18 [D]. Долг пассажира хранит исходное обязательство, погашения и остаток. Предлагаемая M1-политика — запрет новых заказов при подтверждённом непогашенном долге; спорная сумма и grace period регулируются Q-10.
REQ-PAY-19 [D]. Ошибка провайдера и UNKNOWN сами по себе не объявляются подтверждённым долгом. Сначала устанавливается факт оплаты.
REQ-PAY-20 [D]. Переключение карта → наличные после AUTH требует команды, согласия и снятия/сверки холда. Нельзя одновременно списать карту и признать наличное погашение без отражённого излишка/возврата.
REQ-PAY-21 [D]. Чаевые и комиссия за отмену имеют отдельные основания и operation_id; добровольные чаевые не изменяют тариф поездки задним числом.
REQ-PAY-22 [D]. Выплаты M1 — проверяемый реестр с согласованием, отметкой факта внешней выплаты и защитой от повторной выплаты. Автоматическое движение денег включается отдельным адаптером после Q-11.
REQ-PAY-23 [D]. Chargeback не удаляет PAID и поездку: создаёт спор, резерв/корректировку и задачу финансовому сотруднику.

AC-15. Timeout AUTH → поздний успех после отмены вызывает VOID. Timeout CAPTURE не вызывает второй CHARGE. Повторные/перемешанные callbacks не дублируют погашение. Частичная оплата оставляет только непогашенный остаток.

## 17. Финансовый журнал и взаиморасчёты

REQ-LED-01 [D]. Учёт — двойная запись. journal_transaction содержит основание, currency и уникальный business_key; journal_line — счёт, debit/credit, сумму. В каждой транзакции и валюте сумма debit равна credit.
REQ-LED-02 [D]. Журнал append-only. Ошибки исправляются сторно/корректирующей транзакцией с причиной и ссылкой. Балансы — производные; кэш пересчитывается по журналу.
REQ-LED-03 [D]. Типы счетов: дебиторская задолженность пассажира, расчёты с водителем, комиссия службы, расчёты с провайдером, партнёром, чаевые, возвраты, транзит/невыясненные суммы. Юридическое признание выручки/налоги определяется Q-12.
REQ-LED-04 [D]. Блокировка средств AUTH не признаётся поступлением денег. Финансовые факты перевозки, оплаты, удержаний и выплаты разделены.
REQ-LED-05 [D]. Факт завершения и финансовое основание должны надёжно связаться: posting выполняется один раз по final_fare_version через outbox/inbox; при задержке показывается pending accounting и создаётся алерт.
REQ-LED-06 [D]. Нельзя выплачивать неопределённые поступления без согласованной модели авансирования. «Заработано», «погашено» и «доступно к выплате» считаются отдельно.
REQ-LED-07 [D]. Ежедневная сверка сопоставляет локальные операции с провайдером: сумма, валюта, комиссия, возвраты, settlement и пропущенные события. Расхождения имеют владельца и решение.
REQ-LED-08 [D]. У каждой партии выплат уникальный batch_id, состав зафиксирован. Повтор файла/подтверждения не проводит одну строку дважды. Отмена неподтверждённого реестра освобождает резерв, не удаляет журнал.
REQ-LED-09 [D]. Периоды отчётности задаются часовым поясом города/юрлица; сутки не всегда равны 24 часам. Отчёт хранит UTC-границы и timezone.
REQ-LED-10 [D]. Финансовые и операционные коррекции сверяются: полный возврат не меняет автоматически факт выполненной поездки.

Иллюстративная проверка без налогов/комиссии эквайринга: стоимость 10 000 минимальных единиц, комиссия службы 20%, водителю 8 000. При карте полученные 10 000 распределяются на обязательство водителю 8 000 и комиссию 2 000. При наличных водитель уже получил 10 000 и должен службе 2 000; платформа не должна дополнительно перечислить ему 8 000. Это управленческий пример, окончательная схема проводок зависит от юридической модели.

AC-16. Дебеты/кредиты сходятся; повтор события final_fare не создаёт вторую комиссию; наличная поездка не увеличивает безналичную выплату на полную стоимость.

## 18. Партнёрский обмен: M2

### 18.1 Владение и безопасность

REQ-EXC-01 [B]. Инициатор владеет заказом пассажира, исполнитель — своим водителем и его ёмкостью. У каждой стороны локальная запись; общей транзакции PostgreSQL нет.
REQ-EXC-02 [D]. Обмен включает только разрешённые договором города, классы, оплату, лимиты, комиссию, срок и данные. Входящий партнёрский заказ нельзя переслать третьей службе в M2.
REQ-EXC-03 [D]. Идентификатор: origin_instance_id + origin_order_id + exchange_generation. Сохраняются origin и hop_count; hop_count > 1 отклоняется. Повтор webhook и новая попытка — разные понятия.
REQ-EXC-04 [D]. Аутентификация mTLS и/или подписанные запросы с key_id, timestamp, nonce и проверкой повторов; окончательная схема — security review. Ключи ротируются, есть отзыв. Доверенный партнёр всё равно проходит объектные проверки.
REQ-EXC-05 [D]. До подтверждения передаются минимальные данные предложения; контакт пассажира раскрывается только выбранному исполнителю в разрешённом объёме.

### 18.2 Протокол резервирования и подтверждения

| Шаг | Действие | Что запрещено |
| --- | --- | --- |
| 1. Publish | Инициатор публикует предложение с generation и deadline | Считать публикацию назначением |
| 2. Prepare local | Исполнитель резервирует локальную ёмкость водителя и пишет durable intent | Выдавать водителю подтверждённую поездку |
| 3. Reserve origin | Исполнитель запрашивает резерв у инициатора; инициатор атомарно блокирует заказ, возвращает reservation_token и generation | Локальное назначение другому исполнителю при действующем резерве |
| 4. Ready | Исполнитель сохраняет токен, отправляет готовность с operation_id | Забывать локальный резерв при сетевом timeout |
| 5. Commit | Инициатор долговечно фиксирует COMMITTED и outbox; возвращает подтверждение | Повторный поиск после сохранённого COMMIT только по таймауту ответа |
| 6. Confirm local | Исполнитель получает ответ либо читает decision endpoint, переводит назначение в COMMITTED | Подтверждать водителю выполнение без доказанного решения |
| 7. Execute | Идут события прибытия/старта/завершения с sequence и assignment token | Применять события старой generation |
| 8. Reconcile | Обе стороны регулярно сверяют незавершённые exchange | Освобождать неопределённую ёмкость произвольным TTL |

REQ-EXC-06 [D]. До COMMIT инициатор может долговечно зафиксировать ABORT/истечение резерва; поздний READY тогда отклоняется. Если COMMIT уже записан, истечение предварительного срока его не отменяет.
REQ-EXC-07 [D]. Исполнитель после отправки READY удерживает водителя до достоверного COMMIT/ABORT. При недоступном инициаторе состояние остаётся RESERVED/UNCERTAIN, водитель не получает второй заказ.
REQ-EXC-08 [D]. При длительной неопределённости создаётся приоритетная задача. Человек не обходит запрет двойного назначения: разрешение требует согласования с другой стороной и записи нового решения. Цена безопасности — временная недоступность заказа/водителя.
REQ-EXC-09 [D]. После подтверждения перед началом исполнения исполнитель проверяет действительность assignment; при потерянном подтверждении cancellation/commit обе стороны используют decision endpoint. События старого токена сохраняются для аудита, но не меняют актуальную поездку.
REQ-EXC-10 [D]. Отмена COMMITTED — самостоятельный подтверждаемый процесс. До достоверного освобождения старого назначения новый исполнитель не назначается. Если физическое выполнение уже началось, обычное переназначение запрещено.
REQ-EXC-11 [D]. Партнёрские события имеют event_id, exchange_id, generation, sequence, occurred_at. Пропуск sequence вызывает получение снимка. Порядок определяется серверной версией, не временем мобильного устройства.
REQ-EXC-12 [D]. GPS партнёра принимается только по действующему назначению; устаревшие точки не меняют текущую позицию.
REQ-EXC-13 [D]. Расчёт партнёра фиксируется версией договора при принятии, включает payer, cash_collector, commission_basis и currency. Наличные у чужого водителя создают противоположное сальдо, отличное от карточной оплаты инициатору.
REQ-EXC-14 [D]. Акты сверки имеют период, валюту, начальное сальдо, поездки, корректировки, платежи и конечное сальдо. Расхождения не закрываются автоматическим удалением строк.
REQ-EXC-15 [D]. Версии протокола совместимы в опубликованном окне N/N−1; добавления необязательны. Несовместимая сторона не получает новые заказы, существующие доводятся по поддерживаемому контракту.

AC-17. Обрыв на каждом из восьми шагов, повтор READY/COMMIT, отмена во время резерва и рестарт обеих сторон не дают двух подтверждённых исполнителей. При невозможности согласования система явно остаётся в неопределённости и не заявляет успешное восстановление.

## 19. Центральный контур франшизы: M2

REQ-NET-01 [D]. Directory хранит службы, зоны обслуживания, endpoints, версии протокола, публичные ключи и доступность. Поиск партнёра по точке не требует центра в пути обычного заказа: допустим локальный кэш реестра.
REQ-NET-02 [D]. Сетевой режим BLIZZ/FRANCHISE и STANDALONE — конфигурация экземпляра; рабочее название сети подлежит Q-13.
REQ-NET-03 [D]. Центральный контур не собирает пассажирские профили и полные поездки. Любые технические логи проверяются на косвенные персональные данные; отсутствие телефонов не означает автоматическое отсутствие таких данных.
REQ-NET-04 [D]. Royalty принимает отчёт по service_id + city_id + business_date + currency + revision. Повтор той же revision идемпотентен; новая revision заменяет расчёт через корректировку, не стирая прошлую версию.
REQ-NET-05 [D]. База роялти и ставка задаются версией договора с effective_from, минимальным платежом и валютой. Оборот/комиссия, возвраты и округление — Q-14.
REQ-NET-06 [D]. Подписанный отчёт подтверждает отправителя, но не доказывает полноту оборота. Проверяемость требует сверки и договорной модели доступа, не скрытого сбора клиентов.
REQ-NET-07 [D]. Недоступность центра задерживает отчётность и обновление Directory; действующие поездки продолжаются. Нельзя тайно блокировать активные поездки за просроченное роялти.
REQ-NET-08 [D]. При выходе из сети отключаются новые сетевые предложения после завершения текущих обязательств; экспорт и владение данными определяются договором.

AC-18. Отключение центра на сутки не мешает собственной поездке. Повтор/коррекция отчёта не начисляет роялти дважды.

## 20. Уведомления и синхронизация

| Событие | Основной канал | Дополнительный | Критическая проверка |
| --- | --- | --- | --- |
| Новый оффер | WS водителя | Push при допустимом фоне | Серверный срок и действительность при открытии |
| Назначен/сменился водитель | WS пассажира | Push; SMS для телефонного заказа | Только актуальное назначение |
| Прибытие | WS | Push/SMS по политике | Событие подтверждено сервером |
| Отмена/нет машин | WS | Push/SMS | Причина и финансовый результат |
| Оплата/долг/возврат | WS/внутренний inbox | Push без чувствительных деталей | Подтверждённый финансовый факт |
| Документ истекает | Приложение/админка | Push по настройке | Не уведомлять бесконечно |
| Проблема заказа | Рабочее место | Дежурный канал по настройке | Назначен ответственный |

REQ-NTF-01 [D]. Push/SMS не является подтверждением принятия заказа и не гарантирует доставку за секунды. Приложение при открытии получает снимок.
REQ-NTF-02 [D]. Уведомление хранит event_id, recipient, channel, template_version, locale, попытки, next_attempt_at и статус. Дедупликация учитывает событие/получателя/канал.
REQ-NTF-03 [D]. Retry ограничен deadline события; просроченный оффер не отправляется SMS через минуту после назначения другого водителя.
REQ-NTF-04 [D]. Предложенный WS-envelope: event_id, type, schema_version, aggregate_id, aggregate_version, occurred_at, correlation_id, payload. Клиент отбрасывает дубли и устаревшую версию, при разрыве версий запрашивает снимок.
REQ-NTF-05 [D]. Подписка разрешается сервером на конкретный объект и повторно проверяется после изменения прав. Общедоступных topic с телефонами и полной live-картой нет.
REQ-NTF-06 [D]. При WS outage команды остаются REST с идемпотентностью; клиент временно использует ограниченный polling. В интерфейсе показывается потеря оперативного канала.
REQ-NTF-07 [D]. Язык шаблона определяется профилем/заказом, fallback — язык службы. Технические коды ошибок не показываются вместо понятного сообщения.
REQ-NTF-08 [D]. Отказ SMS/Push не отменяет назначение. Неоповещённые телефонные заказы получают задачу диспетчеру.

AC-19. Уведомление старого назначения после переназначения не возвращает старую машину на экран. Отозванный сотрудник теряет подписку на карту.

## 21. Модель данных и правила хранения

Это логическая схема, а не готовая миграция. Обязательные поля и ограничения определены ниже; физические типы и индексы уточняются с измерением запросов, не меняя инварианты.

### 21.1 Общие соглашения

REQ-DATA-01 [D]. Идентификаторы UUID; внешние ссылки включают issuer instance. Время фактов — UTC timestamptz; бизнес-часовой пояс хранится явно. amount_minor bigint + currency char(3); точность валюты из справочника, не жёстко «два знака».
REQ-DATA-02 [D]. Сущности имеют created_at/updated_at, version, author/source по применимости. Исторические события append-only, исправления — отдельные записи.
REQ-DATA-03 [D]. Внутренний order_id отличается от короткого номера для поддержки. Короткий номер не является секретом доступа.
REQ-DATA-04 [D]. Foreign key и уникальные ограничения применяются внутри локального экземпляра. Внешняя ссылка партнёра не изображается локальным FK.
REQ-DATA-05 [D]. Физическое удаление операционных/финансовых записей через обычное CRUD запрещено. Политика анонимизации и удаления файлов — раздел 25.
REQ-DATA-06 [D]. Субъекты сотрудников, клиентов, водителей и партнёров разделены по решению раздела 36. Таблицы принадлежат модулям. Другой модуль обращается к публичному application API или проекции событий. Для критической транзакции назначения order/assignment/trip/driver_capacity принадлежат одному операционному ядру; модуль водителей владеет профилем, а не отдельной конкурирующей истиной о занятости.
REQ-DATA-07 [D]. Read models для админки могут быть eventual consistent. Запись и критическое чтение назначения выполняются с primary. Отставание read replica не используется для решения «водитель свободен».

### 21.2 Каталог сущностей

| Сущность/владелец | Ключевые поля и связи | Ограничения |
| --- | --- | --- |

## 22. API и контракты команд

### 22.1 Общие правила

REQ-API-01 [D]. Contract-first OpenAPI 3.1 для REST и JSON Schema/AsyncAPI для событий. В клиентских приложениях генерируются типы и транспорт; сервер остаётся источником авторизации и инвариантов.
REQ-API-02 [D]. Версия в пути /api/{audience}/v1. Audience: rider, driver, operator, admin. Партнёры /partner-api/v1; webhooks /webhooks/{provider}/{merchantRef}.
REQ-API-03 [D]. Сервер не принимает произвольную смену status через PATCH. Смена состояния — именованная команда с expected_version и command_id.
REQ-API-04 [D]. Идемпотентность: ключ связан с instance+actor+operation и hash нормализованного тела. Повтор с тем же ключом и другим телом → IDEMPOTENCY_CONFLICT; повтор с тем же телом возвращает исходный outcome/resource_id.
REQ-API-05 [D]. command_receipt критических команд хранится весь операционный срок объекта; короткий TTL HTTP-кэша не является единственной защитой от дублей спустя сутки. Для платежей уникальное бизнес-основание сохраняется весь финансовый срок хранения.
REQ-API-06 [D]. Повторная команда обрабатывается после проверки личности; результат идемпотентности возвращается до проверки устаревшей expected_version для того же уже исполненного запроса.
REQ-API-07 [D]. Формат ошибки Problem Details: type, title, status, detail, instance, code, correlation_id, field_errors, current_version по необходимости. Не раскрывать существование чужого объекта; 404 допустим вместо 403 для защиты.
REQ-API-08 [D]. Временные ошибки содержат retryable и retry_after; клиент не повторяет mutation новым command_id автоматически.
REQ-API-09 [D]. Коллекции — курсорная пагинация с устойчивым порядком created_at+id, лимит по умолчанию 50, максимум 100 как предложенный D. Границы дат и часовой пояс явные.
REQ-API-10 [D]. Версия приложения и возможности передаются отдельно от аутентификации. Принудительное обновление не лишает водителя доступа к завершению текущей поездки без безопасного перехода.
REQ-API-11 [D]. Результат асинхронной команды 202 содержит operation_id и endpoint проверки. 200 не означает «банк уже списал», если подтверждена только постановка задачи.

### 22.5 Пример команды и события

Команда принятия: { "command_id": "uuid", "expected_order_version": 7, "offer_id": "uuid", "work_session_id": "uuid" }.
Клиент не передаёт доверенные driver_id, цену и новый статус: водитель определяется сессией, условия — сервером.

Персональные подробности раскрываются адресному получателю, а не кладутся в общую широковещательную тему.

AC-21. Контрактные тесты проверяют все строки реестра соответствующего этапа, схемы ошибок, scope и idempotency. Запрос с тем же ключом и другим телом отклоняется; корректный повтор после timeout возвращает исходный order_id.

## 23. Backend, клиенты и инженерная организация

REQ-ENG-01 [B]. Java Spring, React web и React Native mobile. Модульный монолит — стартовая форма backend. Виртуальные потоки, Spring Modulith, Expo и конкретные UI-библиотеки — варианты реализации, не самостоятельные продуктовые требования.
REQ-ENG-02 [D]. Перед стартом реализации зафиксировать совместимую матрицу JDK/Spring/PostgreSQL/PostGIS/React Native/SDK и дату поддержки. Java 21 — кандидат исходных материалов; версия выбирается проверкой совместимости, а не автоматическим использованием latest.
REQ-ENG-03 [D]. Внутри модуля разделяются domain, application и adapters. Общие типы Money, GeoPoint, IDs минимальны; shared не превращается в доступ ко всем таблицам.
REQ-ENG-04 [D]. Модульные границы и отсутствие циклов проверяются CI. Операционное ядро допускает одну локальную транзакцию для заказа/назначения/ёмкости; удалённый HTTP/банк/маршрутизатор внутри этой транзакции запрещён.
REQ-ENG-05 [D]. Долговечные события реализуются transactional outbox или проверенным механизмом Spring Modulith с повторной доставкой. Нельзя считать обычный in-memory event надёжным outbox.
REQ-ENG-06 [D]. Worker использует lease и идемпотентность; crash после внешнего эффекта и до отметки completed считается штатным сценарием восстановления.
REQ-ENG-07 [D]. Таймауты, retry budget, circuit breaker и bulkhead задаются на каждого провайдера. Повтор POST оплаты/назначения разрешён только с идемпотентным протоколом.
REQ-ENG-08 [D]. Логический монорепозиторий: server, apps/rider, apps/driver, apps/admin, apps/operator, packages/api-client, packages/contracts, packages/localization, deploy, docs. Центральный контур — отдельный deployable module M2.
REQ-ENG-09 [D]. Общие web-компоненты допустимы между admin/operator; мобильные и web UI не обязаны иметь одну библиотеку. Дизайн-система задаёт токены и поведение, не копию предыдущих скриншотов.
REQ-ENG-10 [D]. Frontend может поставляться отдельно или в jar. Упаковка в один jar не является бизнес-требованием; решение зависит от независимости релизов, кэша и эксплуатации.
REQ-ENG-11 [D]. Сборки детерминированы lockfiles, pinned dependencies и неизменяемыми image digests. Секреты не входят в репозиторий, мобильную сборку и публичный bootstrap.
REQ-ENG-12 [D]. Минимальные команды проекта: запуск инфраструктуры dev, backend, web, мобильного dev build; lint, unit, integration, contract, e2e; создание миграции и восстановление тестового бэкапа. README описывает их на чистой машине.
REQ-ENG-13 [D]. Рабочие профили dev/test/stage/prod разделены ключами и данными. Stage не использует production телефоны, токены карт и личные документы.
REQ-ENG-14 [D]. Feature flags серверные и имеют владельца/срок. Выключение функции не повреждает уже начатый процесс, например payment capture или партнёрское назначение.
REQ-ENG-15 [D]. OTA обновления мобильного JS допустимы только при совместимом native runtime и проверенном механизме отката; изменение нативных возможностей требует соответствующего релиза. Офферы не зависят от обещания полноэкранного уведомления на любой ОС.

AC-22. На чистой машине по инструкции проходят сборка и интеграционные проверки; релиз воспроизводим; недоступный провайдер не исчерпывает пул запросов ядра.

## 24. Безопасность, файлы и защита от злоупотреблений

REQ-SEC-01 [D]. TLS для внешних соединений, шифрование носителей/бэкапов и отдельное управление секретами. Внутренние соединения защищаются согласно угрозам инфраструктуры; ключи различаются по экземплярам и средам.
REQ-SEC-02 [D]. Threat model покрывает захват аккаунта, OTP/SMS pumping, подбор чужих IDs, утечку треков, фальшивые документы, GPS-spoofing, ботов «ВСЕМ», мошенничество с наличными и возвратами, поддельные webhooks и недобросовестного партнёра.
REQ-SEC-03 [D]. Сервер ограничивает создание заказов, quote, поиск адресов, принятие офферов и файловые операции. Лимиты различаются по субъекту и ресурсу; один NAT не блокирует целый автопарк без дополнительного анализа.
REQ-SEC-04 [D]. Объектные проверки и field-level redaction обязательны. Водитель после закрытия поездки не получает бессрочный доступ к телефону и live-координатам пассажира.
REQ-SEC-05 [D]. Web защищается от CSRF при cookie auth, XSS, SQL injection, SSRF и небезопасного CORS. URL провайдера/партнёра из админки проходит allowlist/проверку; произвольный доступ к metadata/private сети запрещён.
REQ-SEC-06 [D]. Загрузка файла — краткоживущая scoped upload session: допустимый MIME и фактический тип, размер, hash, quarantine, проверка содержимого и статус SAFE/REJECTED. Имя файла не превращается в путь файловой системы.
REQ-SEC-07 [D]. Фото/документы не публикуются без авторизации. Скачивание через backend либо короткую подписанную ссылку после проверки полномочий. EXIF и лишние метаданные удаляются там, где не требуются доказательству.
REQ-SEC-08 [D]. Отчёты, документы и записи разговоров не попадают в crash analytics. Логи скрывают телефоны, координаты высокой точности, токены, OTP и банковские payload.
REQ-SEC-09 [D]. Ротация мерчанта/подписи предусматривает проверку callback прежним ключом в допустимом окне и повторную сверку. Удаление старого секрета не должно сделать незавершённый платёж непроверяемым.
REQ-SEC-10 [D]. Административный аварийный доступ ограничен временем, обоснован и протоколируется. Прямое редактирование production-БД не является штатной операцией поддержки.
REQ-SEC-11 [D]. Автоматические риск-решения имеют причину и процесс пересмотра. Рейтинг/отказ от заказа не являются единственным основанием необъяснимой постоянной блокировки.
REQ-SEC-12 [D]. Проверки зависимостей, секретов и образов включены в CI. Уязвимости имеют приоритет и срок устранения; исключения документируются.
REQ-SEC-13 [D]. Денежные операции и изменения прав получают усиленный аудит; разделение инициатора и согласующего настраивается. Журнал защищён от обычной правки сотрудником с доступом к интерфейсу.

AC-23. Подмена order_id/file_id/WS-topic не раскрывает чужие данные; вредоносный файл не становится доступным; изменённая подпись callback отклоняется; секрет отсутствует в клиентском bundle и логах.

## 25. Приватность, рынки, фискализация и хранение

Этот раздел задаёт технические механизмы, а не юридическое заключение. Конкретные обязательства, продавец перевозки, получатель платежа, основания обработки и сроки подтверждаются для выбранного рынка до запуска.

REQ-PRV-01 [D]. Для каждой категории данных ведётся реестр: цель, основание, контролирующая сторона, получатели, регион хранения, срок, действие по истечении, legal hold, ответственный.
REQ-PRV-02 [D]. Предлагаемая стартовая политика минимизации: live-позиции вне поездки не сохранять долговременно; треки поездки, записи звонков и документы хранить по утверждённой матрице. Фиктивный универсальный TTL «30 дней для всего» запрещён.
REQ-PRV-03 [D]. Пассажирские данные не передаются центру по умолчанию. Партнёру выдаётся необходимый минимум после назначения; договорное основание и трансграничная передача проверяются отдельно.
REQ-PRV-04 [D]. Запрос удаления проходит идентификацию, поиск всех зависимых данных, анонимизацию допустимых полей и план удаления файлов/кэша. Финансовые обязательства, законное хранение и legal hold не исчезают механически.
REQ-PRV-05 [D]. После восстановления бэкапа повторно применяется журнал удалений/анонимизации. «Удалено в primary» не обещается как немедленное удаление из всех резервных копий.
REQ-PRV-06 [D]. Геокоординаты, устройства, IP и псевдонимы могут оставаться идентифицирующими. Их нельзя объявлять обезличенными только после удаления имени.
REQ-PRV-07 [D]. Экспорт данных пользователя и исправление профиля доступны через проверяемый процесс. Исторические факты корректируются с сохранением аудита, не переписываются без следа.
REQ-PRV-08 [D]. Система хранит версии текстов условий/уведомлений и факт необходимого подтверждения. Разрешение ОС на геолокацию не заменяет все правовые основания.
REQ-FIS-01 [D]. Фискализация за интерфейсом FiscalProvider, если требуется выбранной моделью. Состояния fiscal_document: NOT_REQUIRED, QUEUED, SUBMITTED, ISSUED, FAILED, UNKNOWN, CORRECTED/REFUNDED.
REQ-FIS-02 [D]. Чек связан с юридическим продавцом и финансовым основанием. Не предполагать автоматически, что продавец всегда водитель-ФОП либо сама платформа.
REQ-FIS-03 [D]. Повтор отправки чека не создаёт дубль; UNKNOWN сверяется с провайдером. Возврат и корректировка оформляются связанными документами. Ошибка выдачи создаёт задачу и повтор по разрешённым правилам.
REQ-FIS-04 [D]. Работа без доступного фискального провайдера, offline-режим и право выхода на линию определяются юридической моделью и возможностями провайдера в Q-05, а не техническим предположением.
REQ-FIS-05 [D]. Поддержка нескольких продавцов/мерчантов включает соответствие seller → merchant → fiscal profile. Недопустима оплата на одно юрлицо и чек от другого без утверждённой модели.

AC-24. Матрица хранения заполнена для рынка запуска; удаление профиля не удаляет финансовый журнал; восстановление не возвращает ранее анонимизированный профиль; повтор fiscal callback не выдаёт второй чек.

## 26. Инфраструктура, восстановление и эксплуатация

### 26.1 Профили поставки

| Область | Single-instance | Высокая доступность |
| --- | --- | --- |
| Backend | Одна реплика с рестартом | Несколько реплик по независимым отказовым доменам |
| PostgreSQL | Primary, внешние резервные копии | Primary, репликация, контролируемый failover, PITR |
| Redis | Одна установка, восстановление индексов | Репликация/failover по выбранной топологии |
| Real-time | Локальная доставка допустима | Межрепличная доставка и адресация user sessions |
| Файлы | Локальный диск либо object storage с внешней копией | Отказоустойчивое хранилище с проверенной durability |
| Маршруты/адреса | Общий VPS только после измерения памяти | Отдельная ёмкость и резерв согласно целевому SLA |
| Телефония | Независимый профиль включения | Резерв и маршрутизация SIP-провайдера |
| Оркестрация | Compose/system service как кандидат | Kubernetes либо иной проверенный вариант; не обязательный ради названия |

REQ-OPSINF-01 [D]. Даже бюджетный production-профиль должен иметь копию вне основного сервера. Локальный backup полезен, но не защищает от потери диска/узла. Предложенное правило ужесточает старые материалы и требует утверждения как D.
REQ-OPSINF-02 [D]. RPO/RTO задаются отдельно по аварии узла, зоны и всей площадки. «RPO=0» допускается только в проверенной границе синхронной репликации и корректного fencing; не обещается для утраты всех копий.
REQ-OPSINF-03 [D]. Внешние вызовы и worker безопасны при нескольких репликах. При failover базы старый primary не должен продолжать принимать запись.
REQ-OPSINF-04 [D]. При недоступности Redis новые назначения допускаются только после достаточной проверки пригодности/свежести водителя; можно временно остановить поиск. Действующие поездки читаются из базы.
REQ-OPSINF-05 [D]. При недоступности PostgreSQL критические команды не объявляются успешными. Клиенты показывают pending, сохраняют безопасную очередь; после восстановления проверяется результат до повторной отправки.
REQ-OPSINF-06 [D]. Бэкапы включают БД, объекты, конфигурацию, версии контрактов и доступный процесс восстановления секретов. Ключи восстановления защищены отдельно.
REQ-OPSINF-07 [D]. Минимум ежемесячно выполнять восстановление в изолированную среду с проверкой связности заказа, оплаты, файлов и журнала. Факт создания backup не равен проверке восстановления.
REQ-OPSINF-08 [D]. Релиз проходит dev → CI → stage → пилотный экземпляр → волны. Перед миграцией проверяется совместимость N/N−1, возможность отката кода и forward fix схемы.
REQ-OPSINF-09 [D]. Откат приложения не откатывает внешние списания и опубликованные события. Для них предусмотрены сверка и компенсирующие операции.
REQ-OPSINF-10 [D]. Нужны runbooks: БД, Redis, платёж UNKNOWN, очередь outbox, неверный мерчант, потеря GPS, отказ SMS, компрометация ключа, партнёрская неопределённость, восстановление площадки.
REQ-OPSINF-11 [D]. Отдельно мониторить часы/NTP. Серверные deadlines и токены не должны массово ломаться из-за сдвига времени.
REQ-OPSINF-12 [D]. Миграция службы на другой профиль сохраняет instance_id, данные, внешний домен/ключи по согласованному процессу. Производится freeze/догон репликации и проверка незавершённых операций; простое копирование работающей БД без согласования недостаточно.

| --- | --- | --- |

## 27. Производительность, наблюдаемость и качество интерфейса

### 27.1 Профили нагрузки

REQ-NFR-01 [D]. Нагрузочный тест задаёт одновременно online drivers, orders/sec, конкурентные поиски, GPS/sec, WS-соединения, операторов, долю партнёров и характер отказов. Один показатель «10 000 водителей» недостаточен.

| Профиль | Водители online | GPS | Создание заказов | WS | Назначение |
| --- | --- | --- | --- | --- | --- |
| L1 пилот D | 1 000 | 250/с | 2/с steady, 10/с burst | 2 000 | 15–30 минут проверки |
| L2 старт D | 10 000 | 2 500/с | 10/с steady, 50/с burst | 20 000 | Не менее 2 часов |
| L3 запас D | 30 000 | 7 500/с | 30/с steady, 100/с burst | 50 000 | 2 часа плюс 8 часов soak на L2 |

GPS вычислен при среднем интервале 4 секунды; активные поездки с более частыми точками увеличат поток. Количество соединений и частоты заказов — синтетические гипотезы до Q-16, а не прогноз рынка.

REQ-NFR-02 [D]. Для L2 предлагаются: REST ядра p95 ≤300 мс без внешнего банка/длительного расчёта; принятие заказа p95 ≤500 мс; первый оффер p95 ≤2 с после READY при наличии пригодного кандидата и доступном routing; свежая позиция от приёма сервером до экрана p95 ≤2 с при активном соединении.
REQ-NFR-03 [D]. Время от создания до назначения реального водителя зависит от его ответа; оно измеряется отдельно и не обещается как серверная задержка 2 секунды.
REQ-NFR-04 [D]. Тест фиксирует p50/p95/p99, ошибки, CPU/RAM, DB connections/locks, queue lag и длительность GC. Во время L2/L3 проверяются инварианты, не только throughput.
REQ-NFR-05 [D]. Graceful degradation: ограничение частоты карты и детализации, отказ некритичных отчётов, backpressure GPS; денежные и командные события не выбрасываются ради красивого графика latency.

### 27.2 Наблюдаемость

REQ-OBS-01 [D]. Сквозной correlation_id проходит HTTP, события, worker и provider operations. Трассировка не содержит токенов и точных адресов без необходимости.
REQ-OBS-02 [D]. Метрики: создание/отмена/нет машин, время первого оффера/назначения, принятие/отказы, eligibility exclusions, свежесть GPS, активные назначения, outbox/inbox lag, UNKNOWN платежи, расхождения ledger, возвраты, партнёрские резервы, SMS-затраты.
REQ-OBS-03 [D]. Алерты получают владельца и runbook. Начальные пороги: oldest outbox >60 секунд, UNKNOWN payment >5 минут, партнёрская неопределённость >30 секунд, доля серверных ошибок >1% за 5 минут — кандидаты для пилота, не финальные SLO.
REQ-OBS-04 [D]. Заказы/платежи с ошибкой не исчезают после перезапуска. Поддержка может найти correlation_id и увидеть безопасную временную шкалу.
REQ-OBS-05 [D]. Центральный мониторинг служб собирает минимальные метрики; логи с персональными данными не отправляются в общий центр по умолчанию.

### 27.3 Клиентское качество

REQ-UX-01 [D]. Обязательные состояния каждого экрана: loading, empty, success, validation error, access denied, offline, stale data, retrying. Финансовая неопределённость отображается отдельно от отказа.
REQ-UX-02 [D]. Основные действия доступны при системном увеличении шрифта; контраст и фокус проверяются. Диспетчерские действия поддерживают клавиатуру. Ошибка поля объясняет способ исправления.
REQ-UX-03 [D]. Локализация покрывает тексты, даты, деньги, адреса и множественные формы. На сервере UTC, пользователю время города с понятным timezone в отчётах.
REQ-UX-04 [D]. Официальная матрица устройств/ОС определяется Q-17. Проверки на реальных устройствах обязательны; успешный Expo Go/эмулятор не подтверждает фоновую работу.
REQ-UX-05 [D]. Карты и офферы не требуют идеальной связи; приложение показывает возраст позиции и ожидание подтверждения. Кнопка не изображает успех до серверного результата.

AC-26. Результаты L1–L3 опубликованы с конфигурацией. На L2 нет нарушений инвариантов. На реальных устройствах подтверждены фон, возврат после перезапуска, потеря сети, крупный шрифт и локализация.

## 28. Приёмка, тестирование и критерии готовности

### 28.1 Уровни проверки

REQ-QA-01 [D]. Unit проверяет чистые правила и арифметику; integration — реальные PostgreSQL/PostGIS/Redis и миграции; contract — схемы клиентов/партнёров; e2e — пользовательский сценарий; fault tests — рестарты и сетевые разрывы; load — нагрузку и инварианты.
REQ-QA-02 [D]. Таблицы переходов разделов 9–13 превращаются в параметризованные проверки: разрешённый переход, запрещённый переход, неверная роль, чужой объект, устаревшая версия, повтор, конкурентная команда.
REQ-QA-03 [D]. Свойства для случайных последовательностей команд: не более одного активного назначения на заказ/локального водителя; терминальный заказ не возвращается в поиск; каждая trip имеет assignment; ledger сбалансирован; успешное погашение не дублируется; сумма возвратов не превышает разрешённую.
REQ-QA-04 [D]. Проверка финансовых адаптеров выполняется в sandbox с сохранением обезличенных результатов и сценариями UNKNOWN, повторов, поздних callback и несоответствия суммы.
REQ-QA-05 [D]. Для фоновых режимов использовать реальные устройства, живой и плохой интернет, перезагрузку, force quit, запрет разрешений и изменение времени телефона. Не все ограничения ОС устранимы кодом — приложение должно корректно обнаруживать последствия.
REQ-QA-06 [D]. Для каждого дефекта фиксируются версия, окружение, воспроизведение и критерий исправления. Тест с заглушкой не отмечается как успешно проверенная реальная интеграция.

### 28.4 Definition of Done

Функция считается готовой, когда контракт, данные, права, переходы, ошибки и восстановление реализованы; требуемые проверки проходят; миграции проверены; экран имеет offline/error/pending; метрики и аудит работают; документация и runbook обновлены.

M1 допускается к пилоту после закрытия блокирующих вопросов рынка/денег/доступа, успешного сквозного сценария, проверки реальных мобильных устройств, sandbox платежей, восстановления backup и нагрузочного профиля пилота. Production с целевой нагрузкой требует соответствующего L2/L3 и подтверждённого SLA.

Снимок интерфейса, частичная компиляция, тесты только с заглушками или возможность запуска одного экрана не считаются готовностью продукта.

## 32. Матрица совместного состояния: примеры

| Состояние заказа | Водитель/назначение | Поездка | Оплата | Допустимое действие |
| --- | --- | --- | --- | --- |
| AWAITING_PAYMENT | Нет | Нет | AUTH_PENDING/UNKNOWN | Ждать, сверить, отменить; оффер не отправлять |
| SEARCHING | Нет COMMITTED | Нет действующей | AUTHORIZED либо CASH_EXPECTED | Подбор, отмена, допустимый резерв |
| SEARCHING + резерв M2 | RESERVED | Нет подтверждённого выполнения | Холд/наличные | Завершить COMMIT/ABORT; не назначать второго |
| ASSIGNED | COMMITTED, TO_PICKUP | TO_PICKUP | AUTHORIZED/CASH_EXPECTED | Прибытие, отмена/переназначение по правилам |
| ASSIGNED | COMMITTED, WAITING | WAITING | AUTHORIZED/CASH_EXPECTED | Начало, no-show/отмена по условиям |
| IN_SERVICE | COMMITTED, ON_TRIP | IN_PROGRESS | AUTHORIZED/истёкший холд с задачей | Выполнение, завершение, исключение поддержки |
| FULFILLED | COMPLETED, водитель FREE/NOT_ACCEPTING | COMPLETED | CAPTURE_PENDING/PAID/долг | Финансовое завершение и поддержка, новый заказ водителю |
| CANCELLED до старта | REVOKED/RELEASED | ABORTED либо нет | VOID_PENDING/VOIDED/плата отмены | Сверка и поддержка; старый старт запрещён |
| CANCELLED после старта | Закрыто по исключению | ABORTED с частичным фактом | Частичный расчёт/спор | Коррекция/новый связанный заказ |
| UNFULFILLED | Нет активного | Нет/ABORTED | VOID_PENDING/VOIDED/отказ AUTH | Новый заказ с новым подтверждением |
| Любая активная поездка, связи нет | COMMITTED + DISCONNECTED | Фаза сохранена | Независимо | Задача связи, восстановление; не FREE |
| FULFILLED, callback запоздал | COMPLETED | COMPLETED | UNKNOWN → PAID/FAILED после сверки | Не возвращать поездку в IN_SERVICE |

REQ-CROSS-01 [D]. Недопустимые сочетания обнаруживаются регулярной сверкой и алертом; исправление — предметная команда, не cron UPDATE «сделать всё свободным».
REQ-CROSS-02 [D]. На экране сотрудника видны все четыре оси, а не один общий статус «завершено».
REQ-CROSS-03 [D]. Метрики нарушений инвариантов должны быть равны нулю; любое нарушение — приоритетный дефект с анализом данных и причин.

[PostgreSQL — Partial Indexes](https://www.postgresql.org/docs/current/indexes-partial.html): частичный уникальный индекс может ограничивать уникальность подмножества строк. Для активных назначений используется явный статус, а не зависящий от текущего времени предикат.

[PostGIS — ST_Covers](https://postgis.net/docs/ST_Covers.html): покрытие включает границу геометрии. Выбор приоритета пересекающихся городов остаётся правилом продукта.

[Spring Modulith — Working with Application Events](https://docs.spring.io/spring-modulith/reference/events.html): registry может сохранять сведения о публикациях transactional listeners в исходной бизнес-транзакции. Проверки повторной обработки и внешних эффектов всё равно нужны.

[Expo — Location](https://docs.expo.dev/versions/latest/sdk/location/): фоновая геолокация требует разрешений и специальной конфигурации; поведение при завершении процесса и ограничения платформ проверяются на выбранной версии и устройствах. SDK в продукте фиксируется отдельно.

[WayForPay — Payments](https://wiki.wayforpay.com/en/view/852100) и [Settle](https://wiki.wayforpay.com/view/852113): в документации описаны авторизация/холд, подтверждение списания, возврат и проверка статуса. Договорные возможности мерчанта и работа адаптера проверяются отдельно.

Все правовые/договорные вопросы направлены в реестр Q; фиксированный срок кэша, обязательность кассы и доступность платёжных возможностей не выводятся из предположений.

## 36. Утверждённое уточнение: четыре таблицы пользователей

Дата решения: 26 октября 2026 года. Статус B — прямое указание владельца продукта после подготовки проекта v0.2. Этот раздел имеет приоритет над общими формулировками о пользователях в предыдущих разделах.

### 36.1 Разделение корневых сущностей

| Таблица | Кого хранит | Основные поля |
| --- | --- | --- |
| staff_user | Супер-администратор, администратор, оператор; сотрудники поддержки/финансов при соответствующих правах | id, login/oidc_subject, name, role, permissions, city_scope, state, MFA policy, version |
| client | Клиенты/пассажиры | id, phone_normalized, phone_verified_at, name, language, account_state, has_app, consent refs, version |
| driver | Водители | id, phone_normalized, phone_verified_at, name, language, account_state, review_status, eligibility_rules, version |
| partner | Партнёрские службы такси/организации обмена | id, legal/display name, contact data, exchange endpoint, state, contract refs, allowed cities/classes, version |

Это четыре самостоятельные предметные таблицы. Общей таблицы app_user с клиентами, водителями и сотрудниками в этой модели нет. Вспомогательные таблицы устройств, документов, прав, ключей и журналов допустимы и не объединяют корневые сущности в одну.

Партнёр здесь означает службу/организацию из согласованной модели обмена, а не автоматически водителя, сотрудника или таксопарк с общей клиентской базой. Отдельный интерфейс сотрудников партнёра не входит в M1; если он потребуется, его доступ проектируется отдельным решением.

REQ-USR-01 [B]. Сотрудники, клиенты, водители и партнёры хранятся раздельно в указанных четырёх таблицах.
REQ-USR-02 [B]. SUPER_ADMIN, ADMIN и OPERATOR — роли записей staff_user, не отдельные таблицы и не типы пассажирских профилей.
REQ-USR-03 [D]. Поддержка и финансы — наборы полномочий staff_user либо дополнительные роли той же таблицы. Они не создают пятую корневую таблицу пользователей.
REQ-USR-04 [D]. SUPER_ADMIN управляет сотрудниками, ролями, настройками экземпляра и интеграциями. Он не обходит инварианты назначения, лимиты внешних платежей и аудит. SUPER_ADMIN одного экземпляра не имеет автоматического доступа к другим службам.
REQ-USR-05 [D]. Полномочия ADMIN и OPERATOR задаются матрицей раздела 4. Изменять роли и выдавать SUPER_ADMIN может только отдельное полномочие SUPER_ADMIN с усиленной проверкой.
REQ-USR-06 [D]. Первоначальный SUPER_ADMIN создаётся защищённой процедурой развёртывания, без публичной регистрации и стандартного пароля. Последнего действующего SUPER_ADMIN нельзя удалить/заблокировать без назначенного преемника либо контролируемого аварийного восстановления.

### 36.2 Вход, токены и идентификаторы

REQ-USR-07 [D]. Каждый субъект имеет пару subject_type + subject_id. Типы: STAFF, CLIENT, DRIVER, PARTNER. Одинаковый UUID или телефон в разных таблицах не означает одного субъекта.
REQ-USR-08 [D]. JWT/session содержит subject_type, subject_id, instance_id, audience, session_id и необходимые scope. Токен CLIENT не принимается driver API, а DRIVER не даёт доступ к staff API.
REQ-USR-09 [D]. Телефон уникален по политике активных аккаунтов отдельно внутри client и отдельно внутри driver. Один человек вправе иметь обе записи с одним телефоном; OTP challenge обязательно привязан к audience/type и не открывает второй аккаунт.
REQ-USR-10 [D]. У staff_user уникален login/oidc_subject. Партнёр входит по отдельным машинным ключам/сертификатам, связанным с partner.id; не использует пассажирский OTP.
REQ-USR-11 [D]. Если понадобится единый личный вход человека в несколько ролей, он вводится отдельным согласованным связыванием аккаунтов после подтверждения обоих. Слияния таблиц или автоматического связывания по телефону нет.
REQ-USR-12 [D]. device_session, OTP challenge, audit actor и command receipt включают тип субъекта. Для таких полиморфных ссылок целостность обеспечивается явной проверкой типа/существования либо типизированными FK; не заявлять фиктивный единый FK на четыре таблицы.

REQ-USR-13 [D]. Телефонный заказ может использовать контакт без подтверждённого аккаунта. REQ-USR-14 [D]. Состояния аккаунтов в таблицах различаются от предметных состояний: client может быть UNVERIFIED/ACTIVE/BLOCKED/DELETION_PENDING/ANONYMIZED; driver имеет отдельные account_state и review_status; staff_user — INVITED/ACTIVE/SUSPENDED/DISABLED; partner — DRAFT/VERIFYING/ACTIVE/PAUSED/BLOCKED/TERMINATED.
REQ-USR-15 [D]. Приостановка partner запрещает новые предложения, но сохраняет чтение решений, приём событий и завершение текущих обязательств в ограниченном режиме. Полная компрометация ключа требует отзыва и аварийной сверки через проверенный канал.
REQ-USR-16 [D]. Блокировка одной записи не автоматически блокирует другой тип аккаунта того же телефона. Связанная антифрод-мера требует явного основания и аудита.

AC-27. Таблицы staff_user/client/driver/partner независимы; общего app_user нет. CLIENT-токен с тем же телефоном/UUID не получает доступ к DRIVER/STAFF. SUPER_ADMIN/ADMIN/OPERATOR находятся в одной staff_user. Подмена actor_type и ссылка на несуществующий субъект отклоняются.

### 36.4 Жизненный цикл клиентов, сотрудников и партнёров

| Субъект | Переход | Инициатор/условия | Последствия |
| --- | --- | --- | --- |
| Client | Создание → UNVERIFIED | Служебное создание разрешённого контакта | Нет пользовательской сессии, не подтверждён номер |
| Client | UNVERIFIED → ACTIVE | Успешный OTP и безопасное связывание профиля | Доступ только к подтверждённо принадлежащей истории |
| Client | ACTIVE → BLOCKED | Сотрудник с правом, причина и срок/условие | Новые заказы запрещены, текущая поездка сопровождается |
| Client | BLOCKED → ACTIVE | Проверка причины и разрешение | Долг/спор не исчезает автоматически |
| Client | ACTIVE/BLOCKED → DELETION_PENDING | Подтверждённый запрос | Проверка обязательств, сроков и legal hold |
| Client | DELETION_PENDING → ANONYMIZED | Завершена допустимая обработка | Нельзя войти в старую сессию; сохранены требуемые факты |
| Staff | Создание → INVITED | SUPER_ADMIN/право управления сотрудниками | Приглашение ограниченного срока, без общего пароля |
| Staff | INVITED → ACTIVE | Принято приглашение, настроены вход/MFA | Доступ по выданным scope |
| Staff | ACTIVE → SUSPENDED | Разрешённое административное решение | Отзыв сессий/WS, передача незакрытых задач |
| Staff | SUSPENDED → ACTIVE | Повторное разрешение/MFA при необходимости | Старые сессии не восстанавливаются |
| Staff | INVITED/ACTIVE/SUSPENDED → DISABLED | Увольнение/отзыв, есть преемник критичных прав | Доступ закрыт, история действий сохранена |
| Staff | Смена ADMIN/OPERATOR/SUPER_ADMIN | SUPER_ADMIN с усиленной проверкой | Новая версия прав, отзыв/обновление сессии |
| Partner | DRAFT → VERIFYING | Заполнены данные, ключи и проект договора | Новые реальные заказы ещё запрещены |
| Partner | VERIFYING → ACTIVE | Проверены договор, полномочия, протокол и sandbox | Обмен в пределах опубликованных правил |
| Partner | ACTIVE → PAUSED | Владелец службы/партнёр по договору | Новые предложения запрещены, текущие доводятся |
| Partner | PAUSED → ACTIVE | Повторная проверка доступности/правил | Старые истёкшие предложения не возобновляются |
| Partner | ACTIVE/PAUSED → BLOCKED | Нарушение/риск/компрометация, причина | Новые заказы запрещены, аварийная сверка активных |
| Partner | BLOCKED → VERIFYING | Решение ответственного | Возврат в ACTIVE только после повторной проверки |
| Partner | Любой нетерминальный → TERMINATED | Прекращение договора | Нет новых заказов; сохраняются обязательства/учёт и ограниченный канал закрытия |

В 36.1 account_state клиента дополнен UNVERIFIED для служебного создания. Терминальный ANONYMIZED не превращается обратно в ACTIVE с восстановлением удалённых данных; новая регистрация создаёт новую идентичность по политике службы. DISABLED сотрудник может быть повторно приглашён только отдельной процедурой с новыми сессиями и аудитом. TERMINATED партнёр подключается заново по новой проверке и версии договора.

REQ-USR-17 [D]. Задолженность клиента не заменяется BLOCKED без причины: финансовое ограничение вычисляется отдельно от состояния аккаунта. Погашение долга снимает финансовое ограничение, но не административную блокировку.
REQ-USR-18 [D]. При блокировке сотрудника незакрытые обращения и задания возвращаются в очередь/назначаются ответственному, без потери комментариев и аудита.
REQ-USR-19 [D]. Удаление или блокировка субъекта не освобождает действующее назначение и не аннулирует долг. Закрытие предметных процессов выполняется соответствующими командами.
